# 安装与更新

## 先理解发布方式

Mo.s-Skill 发布的是标准 Skill 目录，而不是一个绑定某个 Agent 的安装器。`skills/<skill-name>/SKILL.md` 是每个 Skill 的入口。

未特别指定时，安装的是**使用版**：复制 `SKILL.md`，再复制该 Skill 运行时需要的 `references/`、脚本或资源；不复制 `evals/`。`evals/` 是维护和回归评测资料，Agent 正常运行不会读取它。需要修改、评测或发布 Skill 时，才安装包含 `evals/` 的**维护版**完整目录。

原有十个个人版的使用版文件如下。每个分发包还需保留适用的 [MIT 许可](<../LICENSE>)；目标 Harness 使用 `agents/openai.yaml` 时同时携带，尤其不能遗漏其中的手动调用策略。

| Skill | 正文及必需参考 |
|---|---|
| [changelog-writer](<../skills/changelog-writer/SKILL.md>) | `SKILL.md`、`references/changelog-format.md` |
| [repository-docs-bootstrap](<../skills/repository-docs-bootstrap/SKILL.md>) | `SKILL.md`、`references/governance-baseline.md`、`references/reproduction-manifest.md`、`references/ticket-governance.md`、`references/bootstrap-checklist.md` |
| [skill-workflow-visualizer](<../skills/skill-workflow-visualizer/SKILL.md>) | `SKILL.md`、`references/workflow-template.md` |
| [skill-workflow-orchestrator](<../skills/skill-workflow-orchestrator/SKILL.md>) | `SKILL.md`、`references/proposal-template.md` |
| `decision-to-spec`、`docs-integrity-audit`、`evidence-based-validation`、`interaction-prototype-to-spec`、`phase-acceptance`、`research-brief` | 各自的 `SKILL.md`；外部方法依赖另按实际任务取得 |

MAT 的六个职责方法不属于 `own`，只按 [For MAT 类型清单](<分层清单.md#for-mat>) 分配，不能一并复制到个人全局目录。

每个 Skill 目录是独立分发单元，必须带齐正文实际引用的文件；不是每份正文都能脱离参考文件单独使用。本仓库不设运行时共享契约目录，也不依赖维护者的本机缓存。

不同 Agent 对 Skill 的发现位置、项目级覆盖规则、插件市场和更新机制并不相同。一个脚本若擅自把文件复制到几个猜测的目录，只能覆盖少数本机配置，也会绕过 Agent 自己的更新和卸载机制。因此请按你使用的 Agent 选择原生方式。

## 新版正文的使用文件与分发边界

本轮新增的正文不是全局安装动作，也不让 `own` 自动包含 MAT 方法。

| 目录／类别 | 使用版必须携带 | 分发边界 |
|---|---|---|
| `research-mos` | `SKILL.md`、`UPSTREAM.md`、`LICENSE`；界面元数据按宿主需要 | Mo’s 通用版，当前会话负责调查，主负责人按既有权限使用辅助 |
| `discernment-nudge-mos` | `SKILL.md`、`UPSTREAM.md`、`LICENSE.txt`；界面元数据按宿主需要 | Mo’s 本地化版，保留 Apache-2.0；日常推荐替换安排未确认 |
| `to-tickets-mat`、`implement-mat`、`review-mat`、`handoff-for-mat`、`hunt` | 各自 `SKILL.md`、`UPSTREAM.md`、`LICENSE` | 只进入对应 MAT 职责目录，不能整组安装进个人全局 |
| `mat-changelog-writer` | `SKILL.md`、`references/changelog-format.md`及根 MIT 许可 | 提交类型专用；当前修订要求唯一提交员跨仓顺序办理批次 |

`evals/` 是维护与评测材料，不是必需运行资源；场景存在不等于运行通过。新正文没有绑定维护者的本机路径或运行时参考缓存。MAT 的角色身份、真实授权、工具和保存机制由接入项目提供，不能只复制目录就宣称业务链可用。

`handoff-for-mat` 必须有用户或有权安排者明确要求，不使用“仅真实人类手势可调用”的设置阻断合法管理安排；正文限制触发不代表系统已实现鉴权。四个原有手动入口保持原策略，不因新增 MAT 方法自动放开。

本仓库 `skills/hunt/` 是 MAT 同名适配源；`recommended`、`all` 仍选择 Waza 的个人 `hunt`，`For MAT` 则明确选择本仓库版本。不能只按名称复制或覆盖，实际有效目录须单独验证。

## 上游参考缓存

维护者可以把上游仓库克隆到 `.skills/upstream/` 作为本机只读参考，并将该目录保持在 `.gitignore` 中。它只用于对照上游正文、核对转交协议和辅助维护，不属于发布内容、安装来源或运行时依赖。

- `skills/`：本仓库维护并发布的自有 Skill，纳入 Git。
- `.skills/upstream/`：上游仓库的本机参考副本，不纳入 Git。
- `manifests/` 和 `docs/`：记录官方来源、Skill 名称和边界，纳入 Git。
- 日常安装和更新：仍使用各 Agent 或上游项目的官方入口。

上游缓存缺失时，本地 Skill 不应因此缺少运行依赖。不得把缓存整体或未经选择的第三方正文打入发布包；本轮明确授权的定向改写作为独立目录维护，并随包保留必要来源、修改说明及许可，不从缓存安装原版冒充改写。

## 方式一：复制到项目

这是最可控的方式。克隆或下载本仓库后，默认只复制需要的使用版文件到你的 Agent 在项目内约定的 Skills 位置。例如：

```text
your-project/
  .agents/
    skills/
      evidence-based-validation/
        SKILL.md
```

项目目录的确切名称由 Agent 决定，常见约定包括 `.agents/skills/`、`.claude/skills/`、`.copilot/skills/` 或工具自己的插件目录。复制后，在该项目发出与 Skill 描述匹配的请求，确认 Agent 能识别它，再安装下一个。只有项目要自行修改或评测该 Skill 时，才复制完整目录和 `evals/`。

优点：Skill 与项目一起审查、版本固定且便于定制。缺点：每个项目都要单独放置一份。

## 方式二：复制到个人目录

如果某个 Agent 支持用户级自定义 Skills，可以将该 Skill 的使用版文件复制到它文档规定的用户目录。只复制 `SKILL.md` 可能遗漏运行时引用文件；但不需要复制 `evals/`。只有维护者需要修改或评测时，才将 `skills/<skill-name>/` 完整复制到用户目录。

Copilot、Claude Code 和 Codex 的当前版本都支持某种用户级或项目级扩展机制，但目录和优先级可能变化。请以各自的官方文档为准，不要把其他 Agent 的目录约定套用过来。

优点：一次安装，可在多个项目使用，且不会把维护评测资料装进日常 Agent 目录。缺点：更新由你负责，也可能和项目局部定制发生覆盖关系。

## 方式三：使用 Agent 的原生安装入口

有些 Agent 支持从 Git 仓库、插件市场或注册表安装扩展。遇到这种情况，优先使用原生入口：

- 它能表达 Agent 自己的权限模型和安装范围。
- 它通常能列出、更新和卸载已安装内容。
- 它不要求本仓库维护所有 Agent 的私有目录规则。

Mo.s-Skill 当前没有为任何单一市场发布专用插件包。原因不是市场方式不好，而是不同市场的元数据、审查要求和行为模型不同。仓库先保持内容层可移植；未来如加入某个市场，会作为明确标注、独立验证的适配层，而不会改变 `skills/` 的规范内容。

## 选择安装范围

开始安装前，先明确选择哪一档。`skills/` 已包含个人、Mo’s 改写和 MAT 专版，**不能把复制整个目录当成 `own` 或个人推荐安装**；按清单指定的来源逐项取得。

| 档位 | 当前清单数量 | 适用目标 |
|---|---:|---|
| `own` | 10 | 原有个人治理方法，不自动扩入新正文或 MAT 专版 |
| `recommended` | 44 | 本仓库 11 项＋上游 33 项；已用 `research-mos` 替换原 `research` |
| `all` | 63 | 保留原有更广精选来源，本次未扩围或替换 |
| `For MAT` | 32 | 27 项类型基础＋5 项手动专题；本仓库 17 项＋上游 15 项 |

逐项来源、类型矩阵和替代关系见[分层清单](<分层清单.md>)。`recommended` 的[来源清单](<../manifests/recommended.json>)明列本仓库与上游来源；`For MAT` 的[独立清单](<../manifests/for-mat.json>)不自动跟随推荐档更新。它们不是安装器、锁定文件或 MAT 运行配置，32 项也不是每个会话都要加载的目录。

`all` 暂保留原 `research`，并非当前推荐档在名称与来源上的严格超集，不应混装原研究入口和新版。`discernment-nudge-mos` 在 MAT 中只给主管，日常推荐的替换仍待确认。安装和卸载需要对应授权，本文同步不直接修改任何个人目录。

需要讨论方案和领域边界时，可使用上游 `grill-with-docs`；需要执行已获准的调查时，采用 [Research](<../skills/research-mos/SKILL.md>)，当前会话负责结论，有资格的主负责人仍可按需使用辅助。`research-brief` 交付任务书不自动启动研究，正文中的旧研究入口建议应按当前配套映射核对。创建、改造或评测 Skill 使用可用的相应维护方法或项目等价流程，不为缺少可选入口自动安装工具。

建议先从一个实际问题开始，而不是一次装完：

| 目标 | 建议先安装 |
| --- | --- |
| 想让每次改动有更可信的验证证据 | `evidence-based-validation` |
| 文档多、多人或多 Agent 协作 | `decision-to-spec`、`docs-integrity-audit` |
| 经常在版本末尾不确定是否完成 | `phase-acceptance`、`changelog-writer` |
| 交互方案需要先体验再决定 | `interaction-prototype-to-spec` |
| 维护或组合多个自定义 Skill | `skill-workflow-visualizer` |

各 Skill 的问题入口、交付物与调用方式见 [README.md](../README.md) 的选择表。

## 更新、定制与移除

1. **更新前先查看差异**：自有 Skill 的行为依赖触发条件、边界和人工确认点，不能只按文件名判断更新是否安全。
2. **项目有定制时优先保留 fork**：把本仓库更新与项目的本地约束合并，而不是无条件覆盖。
3. **原生市场安装的上游 Skill 用其原生命令更新**：不要由 Mo.s-Skill 代替第三方项目管理版本。
4. **移除时删整个 Skill 目录或用原生卸载命令**：不要留下同名的半残目录，以免 Agent 读取到不完整内容。

## 验证安装结果

安装后用一个真实、低风险的请求验证，而不是只检查目录存在。例如安装 `evidence-based-validation` 后，可以让 Agent 为一项已完成的小改动写最小验证卡。检查它是否：

- 先锁定一个明确行为，而不是泛泛列测试；
- 区分已执行证据、待人工步骤和无法证明的边界；
- 没有把离线结果写成真实环境通过。

若 Agent 没有加载 Skill，先检查该 Agent 官方文档中的目录、作用域和是否需要重启或重新打开工作区。
