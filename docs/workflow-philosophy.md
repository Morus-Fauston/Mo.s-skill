# 工作流设计哲学

Mo.s-Skill 不是“让 Agent 自动完成更多动作”的流程集合，而是一套让 Agent 在不确定性中保持边界、证据和决定权清晰的原创工作流设计。`skills/` 中的八个 Skill 是这套设计的具体表达；文档、评测和协作图用于让这套设计可审阅、可维护和可迁移。

## 核心原则

### 从最直接的问题开始

用户不需要先进入一个规定好的大流程。一个明确缺陷先解决缺陷；一处改动先验证这一处；只有多个承诺需要汇总时才进入阶段验收。Skill 之间的箭头表示可能的后续选择，不是自动触发链。

### 区分事实、判断和决定

Git 历史、文件内容、测试输出和真实环境观察是事实；审计结论、版本建议和风险分类是基于事实的判断；产品取舍、规格规则、发布动作和 Git 范围是用户决定。Agent 不能用前两者替代最后一项。

### 让确认点显式可见

涉及产品取舍、未决规则、真实环境、正式文档写入、暂存范围、提交和推送时，Skill 必须说明自己在等待什么确认。确认不是无意义的阻塞，而是把不可逆或高影响动作保留给项目所有者。

### 只做与证据匹配的声明

本机测试、离屏探针、静态阅读、沙箱、真机和生产前环境能证明的事情不同。每个交付物都应明确已执行证据、待人工步骤、阻塞条件和未覆盖范围；不能把“未检查”写成“没有问题”，也不能把局部证据写成全局通过。

### 以职责组合，而不是以工具绑定

每个原创 Skill 应有清楚的输入、输出、边界和转交条件。上游 Skill 可以承担相邻职责，也可以被项目已有的等价流程替换。Mo.s-Skill 关心的是“谁负责把未决问题收敛”“谁负责实际调研”“谁负责验收”，而不是强制某一个插件、目录或安装命令。

## 八个原创 Skill 的分工

| 需要回答的问题 | 原创 Skill | 不应替代的职责 |
| --- | --- | --- |
| 已确认决定应写到哪里 | `decision-to-spec` | 追问未决方案或代替用户拍板 |
| 现有文档是否仍可信 | `docs-integrity-audit` | 重写业务决定或删除历史 |
| 一个改动是否得到足够证明 | `evidence-based-validation` | 判定整个版本是否可交付 |
| 原型体验后怎样形成规格 | `interaction-prototype-to-spec` | 把原型自动升级为生产代码 |
| 一个阶段是否兑现承诺 | `phase-acceptance` | 修复发现的问题或替用户发布 |
| 怎样把调研交给独立 Agent | `research-brief` | 自动派发或自动采纳结论 |
| 怎样记录版本并执行 Git 动作 | `changelog-writer` | 未经确认就暂存、提交或推送 |
| 这些 Skill 如何协作、是否漂移 | `skill-workflow-visualizer` | 用名称或旧图替代实际正文 |

## 上游内容的角色

本仓库不重新分发第三方 Skill。`recommended` 和 `all` 记录的是作者选择过的上游能力与安装范围，用于帮助使用者补齐、比较或替换相邻职责。

它们不改变以下事实：

- `skills/` 下的八个原创 Skill 才是本仓库的发布主体。
- 上游项目不属于本仓库的实现、版本或许可范围。
- `grill-with-docs`、`research` 等推荐搭档不是硬依赖；项目可采用职责等价的既有流程。
- 上游清单变化时，应依据是否仍支持这套工作流哲学来评估，而不是仅按目录数量扩充。

具体协作关系见 [workflows.md](workflows.md)，安装范围和上游清单见 [curated-tiers.md](curated-tiers.md)，许可边界见 [source-attribution.md](source-attribution.md)。
