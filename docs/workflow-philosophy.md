# 工作流设计哲学

Mo.s-Skill 首先是一套帮助使用者理解、可视化和编排自己已有 Skill 的方法，而不是“让 Agent 自动完成更多动作”的流程集合。它让使用者从真实 `SKILL.md` 看清每项能力的触发、边界、输出和转交关系，识别重叠、缺口与低价值项，再形成适合自己的可维护工作流。`skills/` 中的九个原创 Skill 是这套方法的示范实现与关键能力；文档、评测和协作图用于让方法可审阅、可维护和可迁移。

## 先理解，再编排

工作流优化从盘点现状开始，而不是从安装新工具开始：

1. 用 `skill-workflow-visualizer` 读取现有 Skill 的真实正文，生成选择表、工作流图与可选的历史聚合信号。
2. 用 `skill-workflow-orchestrator` 根据这些事实指定主入口，并区分自动动作、用户选择、条件建议和外部执行。
3. 由 `skill-workflow-orchestrator` 找出职责重叠、缺失能力、失效流程图、历史产物与不应默认安装的项，提出精简、替换或补充候选。
4. 用户确认新 Skill 候选后，转 `skill-creator` 设计、评测和迭代；用户确认编排变更后，才修改工作流文档、安装范围或 Skill 清单。

九个原创 Skill 的价值不仅在于可直接使用，也在于为“从问题到主入口、从主入口到条件转交”的编排方式提供可复核范例。

## 核心原则

### 从最直接的问题开始

用户不需要先进入一个规定好的大流程。一个明确缺陷先解决缺陷；一处改动先验证这一处；只有多个承诺需要汇总时才进入阶段验收。Skill 之间的箭头表示可能的后续选择，不是自动触发链。

### 区分事实、判断和决定

Git 历史、文件内容、测试输出和真实环境观察是事实；审计结论、版本建议和风险分类是基于事实的判断；产品取舍、规格规则、发布动作和 Git 范围是用户决定。Agent 不能用前两者替代最后一项。

### 让确认点显式可见

涉及产品取舍、未决规则、真实环境、正式文档写入、暂存范围、提交和推送时，Skill 必须说明自己在等待什么确认。确认不是无意义的阻塞，而是把不可逆或高影响动作保留给项目所有者。

### 只做与证据匹配的声明

本机测试、离屏探针、静态阅读、沙箱、真机和生产前环境能证明的事情不同。每个交付物都应明确已执行证据、待人工步骤、阻塞条件和未覆盖范围；不能把“未检查”写成“没有问题”，也不能把局部证据写成全局通过。

### 按需求编排，而不是堆积 Skill

工作流的质量不由安装数量决定，而由“遇到一个真实问题时，能否快速选到唯一主入口、知道何时转交、知道何时停止”决定。一个 Skill 只有在补齐明确缺口时才值得保留；名称相近、输出重叠、依赖前提不成立，或仅是空模板和历史产物的目录，都不应混入可用集合。

这意味着维护时应持续做三件事：

1. **明确主入口**：为报错、规划、已确认决定、单改动验证、阶段验收、发版等问题分别指定最直接的 Skill，而不是让多个同类 Skill 同时竞争触发。
2. **保留有条件的转交**：相邻 Skill 只在前提满足时进入，例如计划已批准后才实施、根因不明才转排查、阶段验收前先证明具体改动。
3. **删除或降级冗余项**：功能已被主入口覆盖、没有实际使用场景、仅是占位模板或运行产物时，删除它；仍有少量专门用途但不应默认安装时，降为按需参考。

工作流文档应先给出“问题 -> 主 Skill”的总览和直接入口表，再说明例外、人工关口与后续转交路线；不应按安装来源罗列所有可能工具，迫使使用者自行猜测从哪里开始。

### 先可视化，再编排

推荐使用 `skill-workflow-visualizer` 作为个人或项目整理 Skill 工作流的起点。它不根据名称、旧流程图或使用习惯猜测关系，而是读取当前 `SKILL.md`，提取每个 Skill 的触发条件、前提、自动步骤、人工关口、输出和禁止项，整理为可审阅的选择表和 Mermaid 工作流图。

完成可视化后，使用 `skill-workflow-orchestrator` 根据真实关系编排工作流：

1. 指定每类问题的主入口，消除同类 Skill 的竞争触发。
2. 标记只有在前提满足时才进入的转交路径，避免把所有 Skill 排成必经流水线。
3. 找出缺失能力、职责重叠、过期流程图和不应默认安装的项。
4. 经用户确认后，更新项目工作流文档、安装范围或 Skill 清单；确认创建或改造 Skill 时转 `skill-creator`；没有确认时，只交付方案和待核实项。

因此，`skill-workflow-visualizer` 是事实与可视化入口，`skill-workflow-orchestrator` 是重编排入口，`skill-creator` 是创建与迭代入口；三者共同维护这套“少而准、按需求编排”的哲学。

### 以职责组合，而不是以工具绑定

每个原创 Skill 应有清楚的输入、输出、边界和转交条件。上游 Skill 可以承担相邻职责，也可以被项目已有的等价流程替换。Mo.s-Skill 关心的是“谁负责把未决问题收敛”“谁负责实际调研”“谁负责验收”，而不是强制某一个插件、目录或安装命令。

## 九个原创 Skill 的分工

| 需要回答的问题 | 原创 Skill | 不应替代的职责 |
| --- | --- | --- |
| 已确认决定应写到哪里 | `decision-to-spec` | 追问未决方案或代替用户拍板 |
| 现有文档是否仍可信 | `docs-integrity-audit` | 重写业务决定或删除历史 |
| 一个改动是否得到足够证明 | `evidence-based-validation` | 判定整个版本是否可交付 |
| 原型体验后怎样形成规格 | `interaction-prototype-to-spec` | 把原型自动升级为生产代码 |
| 一个阶段是否兑现承诺 | `phase-acceptance` | 修复发现的问题或替用户发布 |
| 怎样把调研交给独立 Agent | `research-brief` | 自动派发或自动采纳结论 |
| 怎样记录版本并执行 Git 动作 | `changelog-writer` | 未经确认就暂存、提交或推送 |
| 这些 Skill 如何协作、是否漂移 | `skill-workflow-visualizer` | 用名称或旧图替代实际正文 |
| 如何重编排、精简已有 Skill 或发现新 Skill 候选 | `skill-workflow-orchestrator` | 根据名称猜行为，或未经确认创建、删除或安装 Skill |

## 上游内容的角色

本仓库不重新分发第三方 Skill。`recommended` 和 `all` 记录的是作者选择过的上游能力与安装范围，用于帮助使用者补齐、比较或替换相邻职责。

它们不改变以下事实：

- `skills/` 下的九个原创 Skill 才是本仓库的发布主体。
- 上游项目不属于本仓库的实现、版本或许可范围。
- `grill-with-docs`、`research` 等推荐搭档不是硬依赖；项目可采用职责等价的既有流程。
- 上游清单变化时，应先检查它是否填补明确需求、是否与现有主入口重叠、是否具有可执行的转交条件；不因目录数量或来源热度而扩充。
- `all` 是作者当前筛选结果的记录，不是鼓励任何使用者安装全部内容的清单。

具体协作关系见 [workflows.md](workflows.md)，安装范围和上游清单见 [curated-tiers.md](curated-tiers.md)，许可边界见 [source-attribution.md](source-attribution.md)。
