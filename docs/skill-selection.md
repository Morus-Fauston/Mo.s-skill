# Skill 选择指南

这八个 Skill 是相互配合的工作流，不是八条必须依次执行的命令。先回答“我现在最直接要解决什么”，再选择一个主入口。

## 快速选择

| 当前需求 | Skill | 它解决什么 | 它不解决什么 |
| --- | --- | --- | --- |
| 验收一个阶段、版本或里程碑 | `phase-acceptance` | 从承诺中提取验收项，区分自动、静态、人工和真实环境证据 | 不修复问题，不替代代码审查 |
| 将已经确认的结论写入正式文档 | `decision-to-spec` | 给决定找唯一主要来源，并同步派生文档和索引 | 不把候选方案写成定案 |
| 迁移、整理或交接前检查文档 | `docs-integrity-audit` | 检查入口、链接、状态、术语、权威来源和历史路径 | 默认不改动业务决定或重写文档 |
| 证明一个具体改动是否验证充分 | `evidence-based-validation` | 为一个行为选择最小有效验证，并留下证据边界 | 不回答整个版本是否可交付 |
| 复杂操作流程需要先点一点再决定 | `interaction-prototype-to-spec` | 做可体验原型，把确认结果写成可验收的交互契约 | 不把原型直接当生产实现 |
| 需要独立 Agent 调研源码、竞品或技术路线 | `research-brief` | 写出范围、证据、交付物和接收条件明确的调研任务书 | 不自动派发、不执行实际调研 |
| 准备发版，想记录改动并决定 Git 动作 | `changelog-writer` | 根据 Git 事实起草两个层次的更新日志，并等待一次确认 | 不替代功能验证或发布验收 |
| 维护多个 Skills，担心流程图或触发规则过期 | `skill-workflow-visualizer` | 从真实 `SKILL.md` 提取触发、关口、输出和转交关系 | 默认不修改被分析的 Skill |

## 四条常见路线

### 已确认的技术或产品决定

```text
需要事实时先调研
  -> 用户确认是否采纳
  -> decision-to-spec
  -> 实现
  -> evidence-based-validation
  -> phase-acceptance
```

`research-brief` 只在调研值得委托给独立 Agent 时出现。它交付任务书，不代替实际调研，也不替用户采纳建议。

### 复杂交互

```text
交互理解不一致
  -> interaction-prototype-to-spec
  -> 用户体验并确认规则
  -> decision-to-spec
  -> 实现和验证
```

原型只能证明被模拟的体验，不能证明生产代码的性能、权限和原生控件行为。

### 文档治理

```text
重命名、迁移或准备交接
  -> docs-integrity-audit
  -> 修复已证实的机械问题
  -> decision-to-spec（仅当已有决定需要同步）
```

审计发现冲突时，应先确认权威来源，不要让 Agent 擅自选择一个版本。

### 发布准备

```text
完成实现
  -> evidence-based-validation
  -> phase-acceptance
  -> changelog-writer
```

测试通过不是阶段通过；阶段验收通过也不授权自动提交或推送。`changelog-writer` 会在写入更新日志和任何 Git 动作前等待用户确认。

## 共同原则

1. **从当前问题开始**：不因为一套 Skill 都可用，就让它们全部运行。
2. **未确认就是未确认**：候选方案、猜测、调研建议和原型偏好不能自动升级为项目决定。
3. **证据要说清边界**：本机、离线、模拟、真实浏览器、预发布和生产环境的证明力不同。
4. **确认点必须可见**：涉及产品取舍、真实环境、正式文档写入和 Git 操作时，Agent 应说明自己在等待什么。
5. **项目规则优先**：每个 Skill 都应服从当前项目的指令、目录、命名、语言和验证要求。

具体协作关系见 [workflows.md](workflows.md)。
