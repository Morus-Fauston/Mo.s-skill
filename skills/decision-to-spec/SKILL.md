# 决策同步到规格

这个 Skill 处理的是“讨论已经收敛，接下来把结论放到正确位置”。它的价值不在于多写一份大文档，而在于让同一个决策只有一个现行含义，并且让未来的 Agent 能找到它、理解它、按它执行。

## 完成条件与上下文摘要

- 维护参考：`skills/_shared/references/work-item-contract.md`、`skills/_shared/references/confirmation-gates.md`。
- 完成条件：每条已确认决定都有主要来源、派生引用、一致性检查结果和未决/阻塞说明。
- 同一上下文继续工作时直接沿用当前信息；只有跨 Agent、跨会话或长期留档时，才摘要已确认决定、主要来源、更新文档、证据、未决问题和下一步。
- 缺少完整功能规格时调用 `to-spec`；只有文档机械问题时调用 `docs-integrity-audit`。

## 操作边界

- 只同步已经明确确认的结论。`A/B` 选择、用户说“先跳过”“之后再讨论”、未验证假设和待调研问题不能写成现行决策。
- 本 Skill 只负责已确认决定的文档归属、同步和一致性检查。若项目还缺少完整的功能规格、验收契约或实现边界，先转交上游 `to-spec`，不要在这里重新生成一份完整规格。
- 允许编辑项目文档，但不修改产品代码、不执行部署、不提交或推送 Git。重命名/移动文档前先检查工作区状态和现有引用。
- 遵循项目已有的目录、编号、语言、文档模板和项目指令；不要把通用模板硬套到不同项目。
- 项目中的术语表或领域模型文档只放稳定术语和领域定义，不放实现步骤、临时计划或完整规格。
- ADR 只记录难逆转、未来读者会疑惑、且经过真实权衡的架构决策。普通交互细节不要滥写 ADR。
- 如果无法判断结论是否已确认、文档是否应公开、或某个冲突哪一方是现行规则，停止写入并列出需要用户确认的问题。
- 纯文档改名、移动、索引、旧路径、标题锚点、重复文件或完成状态核对，且没有待同步的已确认决策时，转用 `docs-integrity-audit`，不要为了完成任务虚构决策落点。

## 工作流程

### 1. 提取决策状态

先读取当前对话中做决定的上下文，再读取项目的术语表/领域模型、现行决策记录、需求文档、设计/技术规格、开发规划、工作流说明和文档索引。必要时读取邻近代码确认文档说法没有明显违背实现；不要为了“全面”扫描无关代码。

把讨论内容分为四类：

| 状态 | 处理方式 |
| --- | --- |
| 已确认决策 | 同步到现行文档，并保留必要的理由和边界 |
| 未决问题 | 记录在讨论记录、待决策清单或 backlog，不进入现行规格 |
| 待调研事实 | 生成或更新调研任务书/研究入口，标注不能据此开发 |
| 已废弃决策 | 从现行文档移除或标记废弃，保留历史追踪和替代决策 |

每条已确认决策都保留最小追踪信息：决定了什么、为什么、影响哪些范围、是否有例外、落在哪些文档。不要把整段聊天原样倾倒进正式规格。

### 2. 选择文档归属

按内容分配，不按用户随口提到的文件名分配：

| 内容 | 首选位置 |
| --- | --- |
| 稳定领域术语、对象定义、边界 | 项目的术语表或领域模型文档 |
| 难逆转的架构取舍及理由 | 项目的 ADR 或架构决策目录 |
| 用户问题、目标、范围、用户故事 | PRD |
| 具体字段、交互、状态、接口和验收条件 | 设计/技术规格书 |
| 分阶段顺序、依赖、交付方式 | 开发规划/路线图 |
| 反复执行的操作步骤和输入输出 | 工作流文档 |
| 未决问题、待调研事项、历史讨论 | 辅助文档、研究任务书或归档目录 |

同一事实可以在多个文档被引用，但只能有一个主要来源。其他位置用链接或简短摘要，不复制一整套容易漂移的规则。

### 3. 先做变更映射，再编辑

编辑前先列一张内部映射：

```markdown
| 决策 | 主要来源 | 需要更新 | 只需引用 | 不应修改 |
| --- | --- | --- | --- | --- |
| [稳定术语] | 术语表 | 术语表 | 需求文档、规格 | 历史记录 |
```

检查每个目标文件当前的状态、编号和写作格式。对于重命名或移动，先找全文引用、索引、README 入口、相互链接和旧路径；不要只改文件名。

### 4. 编辑并同步状态

按“主要来源 → 派生文档 → 索引”顺序更新。同步时：

- 将旧方案标为废弃或历史，不让它继续看起来像现行方案；
- 更新版本、状态、完成标记和依赖关系；
- 保留必要的决策理由和不适用范围；
- 更新目录索引、相对链接、标题锚点和交叉引用；
- 不为了整齐重排无关章节，不进行与当前决策无关的大规模改名；
- 不能确定的内容写成“待确认/待调研”，不能自行补答案。

### 5. 一致性审计

编辑后检查：

1. 同一术语是否在术语表、决策记录、需求文档和规格中含义一致；
2. 现行文档是否还保留与新决策冲突的旧说法；
3. 已完成项是否仍被标成未完成，未完成项是否被误标为已完成；
4. 文档链接、索引路径、编号和文件名是否有效；
5. 规格中的范围、验收条件和开发规划是否互相匹配；
6. 是否把待调研事实误写成可以直接实现的结论。

发现冲突时先按来源优先级判断：当前明确决策 > 最新 ADR/现行规格 > 旧规划 > 历史文档。无法判断时不要擅自覆盖，列为阻塞问题。

### 6. 输出迁移/同步报告

在项目已有文档记录目录写入简短报告；若目标目录或公开范围不明确，先询问。报告必须包含：

```markdown
# 文档同步报告

## 结论
- 同步状态：完成 / 部分完成 / 阻塞
- 已确认决策：X 条
- 已更新文档：X 个
- 已修复链接/索引：X 处
- 待确认或待调研：X 条
- 发现冲突：X 条

## 决策落点
| 决策 | 状态 | 主要来源 | 更新位置 | 备注 |
| --- | --- | --- | --- | --- |

## 文档变更
| 文件 | 变更 | 原因 |
| --- | --- | --- |

## 一致性检查
- 术语：通过 / 问题
- 旧方案残留：通过 / 问题
- 完成状态：通过 / 问题
- 索引和链接：通过 / 问题
- 规格与规划：通过 / 问题

## 未决与阻塞
- [仍需用户确认或外部调研的事项]

## 后续动作
- [具体可执行动作]
```

如果没有发现某类问题，也明确写“本轮未发现”，不要让空表看起来像漏检查。报告中的“已完成”只表示本次确实检查或写入过的内容。

## 与相邻 Skill 的边界

- 用 `grill-with-docs` 逐个追问、挑战方案并在决策形成时更新术语；本 Skill 接手已经形成的结论。
- 用 `think` 规划版本和方案；不要在本 Skill 中重新替用户做产品决策。
- 用 `to-spec` 生成面向 Agent 的完整功能规格；本 Skill 可以先整理决策落点，但不强制发布 issue。
- 用 `check` 审查代码、发布和 Git 状态；本 Skill 只检查文档一致性。
- 用 `phase-acceptance` 验收实现是否达到规格；本 Skill 只负责让规格本身可追踪、可找到、少冲突。

## 常见误判

- 用户说“写进去”不代表所有讨论内容都已批准；先按状态分流。
- ADR 数量多不代表文档治理好；普通 UI 细节不应被包装成架构决策。
- 把同一规则复制到五份文档不是同步，而是制造五个未来冲突源。
- 文件移动成功不等于文档整理完成；索引、链接、README 和历史引用也必须检查。
- “没有找到冲突”只有在明确检查过术语、状态、链接和范围后才成立。
