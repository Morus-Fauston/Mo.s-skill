# Skill 工作流重编排

依据实际触发、判断、权限和产物，找出会造成误调用、重复工作或遗漏的流程，再提出可审阅的调整。默认只交方案；已有明确改造授权时复用授权范围，不重复确认。

## 1. 建立当前事实基线

优先复用当前 `skill-workflow-visualizer` 结果，并核对涉及的正文是否变化。没有现成图时，直接读取范围内的 `SKILL.md`、调用配置、必要引用和项目规则，建立简短事实表，不要求用户先运行另一个 Skill。

事实表至少记录路径/作用域、触发、关键判断、人工关口、输出和条件转交。不能只凭名称、描述或记忆建议删改；无需为简单关系先画图。需要完整可视化时可建议用户主动调用 visualizer，不隐式启动仅手动 Skill。

只有用户明确授权跨项目历史分析时才使用可访问历史，并把聚合观察与当前正文事实分开。频率不是保留或删除的充分理由；跨 Agent 同名运行副本也不是独立重复来源。

## 2. 判断改动是否真正有收益

对每项候选回答“去掉或改写这一条，会改变哪个实际任务中的行为？”：

| 候选 | 需要的证据 |
| --- | --- |
| 收敛主入口 | 同一请求竞争触发，且输出/职责重叠；指出首选入口和剩余项的条件 |
| 补转交或边界 | 具体任务出现遗漏、停滞、误写入或重复执行 |
| 精简正文 | 同一 Skill 内重复，或文字不能改变触发、判断、权限、证据或输出 |
| 降为参考 | 仅某类任务需要的长模板、例子或程序说明；保留清晰读取条件 |
| 新 Skill | 多次出现的稳定任务，现有入口或一条边界修正不能承接，且有可验证收益 |

精简候选要指向具体段落/行号和受影响场景，不能只说“模型必然知道”或“看起来长”。规则同时出现在两个可独立安装的 Skill 中，可能是各自不可缺的边界，不因重复自动删除。已被评测覆盖的规则先确认保留了行为，再考虑缩短；必要确认门和证据约束不受“一行以内”等长度指标限制。

新 Skill 候选写明输入、触发、核心判断、输出、不负责什么、现有能力缺口和至少两个真实评测场景。用户历史不足时只作为假设，不编造重复频率。

## 3. 交付可选择的方案

按影响排列已证实的问题和候选。每项给出证据、建议变化、预期收益、代价与所需授权；把事实、历史观察和建议分开。

少量调整直接给“问题 → 改法 → 验证方式”；涉及多个入口或新 Skill 时按需读取 [方案模板](references/proposal-template.md)。图只表达有帮助的分支关系，不能把建议画成已生效工作流。

评价标准是是否减少误触发、重复确认、无效检查或产物遗漏，不是目录数量、正文行数或调用次数本身。

## 4. 在授权范围内执行

默认只读方案不修改文件。用户确认具体改造后，将候选契约、边界与评测场景交给可用的 `skill-creator` 或项目等价 Skill 维护流程；可在当前上下文继续，无需另开任务。

已有授权覆盖的改造直接进行。新增的删除、安装、卸载、目录移动或清单变化需有对应授权；这些不是正文改写的附赠动作。删除前落实准确路径、作用域和影响，遵守项目清理规则；已明确批准同一范围时不再机械重复提问。

修改后核对路由、正文、引用和调用配置是否一致，并使用真实正例与近似反例验证行为。安装前后的发现与运行需另有实际证据，不能用源码检查替代。

交付最终变化、实际验证和剩余不确定性。只在跨 Agent 或跨会话时补事实基线、已批准范围和下一步摘要。
