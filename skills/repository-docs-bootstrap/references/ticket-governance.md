# 票据管理基线

这份基线把 Mo's 仓库中反复使用的本地票据、期次入口和执行证据整理成可复现契约。票据不是 GitHub Issue 的镜像，也不是正式规格的替代；它是一次得到授权的实现或验证切片的执行合同。

## 目录结构

```text
.scratch/
├── README.md
├── <版本或功能主题>/
│   ├── README.md
│   ├── 规格.md                  # 可选，临时规格，不替代正式 Docs
│   ├── issues/
│   │   ├── 01-<中文主题>.md
│   │   └── 02-<中文主题>.md
│   ├── evidence/
│   │   ├── 01/<运行批次>/
│   │   └── 02/<运行批次>/
│   ├── goals/                   # 可选：启动文本或阶段目标，不是票据
│   └── work/                    # 可再生中间文件
├── research/                    # 调研缓存，不是正式 Research 报告
├── tool-cache/                  # 本机工具缓存
├── 证据二进制池/                 # 可选：按 SHA-256 复用大型证据
└── 文档治理/                     # 可选：迁移、去重和布局核查
```

`.scratch/README.md` 是总入口；版本/功能 README 只提供范围、票据、依赖、证据和正式文档导航，不复制每张票的实时状态。没有实际票据或证据时不创建假结果目录；需要保留目录语义时放一个 README，说明当前状态。

## 票据文件命名和语言

票据文件名、标题、说明、Checklist、讨论记录和验收记录使用简体中文；代码标识符、命令、路径、正式研究编号和外部工具名称可以保留原文：

```text
.scratch/v030/issues/01-统一精灵图写入能力.md
.scratch/二期开发/issues/06-完成二期期末演示与人工验收.md
```

一个文件只描述一张票。票号按该版本/主题的依赖顺序从 `01` 递增；票号不是完成顺序的自动证明，也不因封存或迁移重新使用。

## 必需头部

每张活跃票据顶部必须有当前依赖和唯一当前状态：

```markdown
依赖于：无 / 票据编号
状态：ready-for-agent
```

可以再放所属期次、规格依据、责任人和创建日期，但不要把实时状态只放在版本 README、依赖图或聊天记录中。票据头部是单票状态的唯一来源；导航页只链接或注明快照日期。

## 状态机

默认使用以下六种状态：

| 状态 | 含义 | 谁可以更新 |
| --- | --- | --- |
| `ready-for-agent` | 范围已授权、依赖已满足，可以领取；不表示已开始 | 维护者确认范围与依赖；Agent 可依据明确授权登记 |
| `in-progress` | Agent 正在执行已授权切片 | 执行 Agent |
| `awaiting-human` | 自动化实现/材料已完成，等待人工操作、真实环境验收或最终处置 | Agent 提交材料；维护者确认人工结果 |
| `blocked` | 明确外部结果、授权或依赖缺失，当前步骤无法继续 | 发现者记录；责任人确认解除 |
| `completed` | 当前 Checklist 全部满足，所需人工结果有可追踪记录 | 维护者确认；只有明确预授权的纯自动化票据可由 Agent 登记 |
| `archived` | 维护者明确停止或封存，不再领取 | 维护者决定 |

默认转换为：

```text
ready-for-agent -> in-progress -> awaiting-human -> completed
                                      └───────────> blocked
```

无人工要求的票据可以从 `in-progress` 进入 `completed`，但必须附完整自动化证据。`archived` 不表示完成，`blocked` 不等于待人工验收；不要用测试退出码为零代替 Checklist 或人工门。

失败后追加失败项、复现命令、证据入口和影响范围；仍在原授权范围内修复时回到 `in-progress`，需要新范围、决定或外部授权时先转 `blocked` 或等待维护者确认。维护者调整验收范围时，必须在票据中记录调整原因、确认人、日期，并保留原始条件和已有证据，不能通过删除 Checklist 取得 `completed`。封存票据保留未完成项和失败证据；重新研究或重新实现默认创建新票据并链接旧票，不自动恢复封存票。

## 票据正文契约

新票或活跃票至少包含：

```markdown
# <中文主题>

依赖于：无
状态：ready-for-agent

## 规格依据
- 当前决策/规格/ADR：

## 目标与范围
- 要实现或验证：
- 不包含：

## 验收清单
- [ ] 每一项都是可判定的完成条件

## 当前证据
- 自动化命令和结果：
- 证据入口：
- 未覆盖项：

## 剩余动作
- 下一责任人：
- 所需人工结果或解除条件：

## 讨论记录

## 验收记录
```

Checklist 是验收事实：完成一项才勾选一项，不能只改状态不勾选。`completed` 必须全部勾选并保留验收记录；`awaiting-human` 和 `blocked` 必须写明剩余动作、所需结果、下一责任人和解除条件。

## 依赖与领取

- 创建票据不等于授权实施；`ready-for-agent` 必须同时满足范围、规格和前置依赖。
- 领取前读取当前决策、规格、ADR、票据头部和依赖证据；不能仅按票号顺序假设依赖已满足。
- 前置票为 `awaiting-human` 时，后续票只有在明确不依赖剩余人工结论、且自动化依赖证据已满足时才能继续。
- 票据状态不直接映射 Agent Goal、CI 状态或 GitHub Issue 状态；工具状态不能反推项目已验收。
- 依赖、范围或验收条件发生实质变化时，先在票据中记录变化原因和确认人，再继续执行。
- 若维护者预先批准一组连续期次或并行票据，授权必须记录适用范围、启动指令、停线条件、负责人和共享文件边界；它不自动跨越未满足依赖、重大范围变化或人工验收门，也不把其他仓库的授权复制到新仓库。

## 证据与交接

每张票链接自己的 `evidence/<票号或验证主题>/<运行批次>/`。证据记录代码提交和未提交改动范围、命令、环境、结果、原始文件位置、人工反馈和未覆盖项。按需分开记录单元/集成自动化、进程或端到端冒烟、真实桌面/设备/生产前环境和人工观察；一层证据不能冒充另一层。原始日志、截图、JSON 和二进制不因目录整理改写；迁移必须记录旧路径、新路径和哈希。

对外或跨 Agent 交接时，票据补充：输入代码基线、授权范围、已完成工作、自动化结果、人工结果、未验证项、下一责任人和回传方式。维护者接收后重新核对当前主来源和并行改动；回传不会自动成为正式决定或验收结论。

Agent 不得自行执行或宣称完成需要维护者/用户的真实桌面、真机、生产前环境、账号权限或内容安全验收；只能准备手册、自动化材料和待人工项。人工结果必须由维护者写入验收记录，包含环境、日期、观察范围和未覆盖项。

## 与正式文档的边界

- `.scratch` 保存执行合同、临时规格、证据和工作文件；不替代 `CONTEXT.md`、当前决策、ADR、正式 Research 或规格。
- 已确认且可复用的结论通过 `decision-to-spec` 同步到正式 Docs；票据只链接主来源。
- Research 缓存归 `.scratch/research/`，正式任务书/报告归 `Docs/Research/` 或项目等价目录。
- 阶段/版本验收结论进入 `phase-acceptance` 或正式验收/发布资料；票据保留具体执行证据和链接。
- 文件迁移、票据整理和证据归位不能自行改变验收结论、关闭票据或恢复封存工作。
