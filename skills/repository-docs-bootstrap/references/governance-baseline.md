# 治理骨架基线

这份基线以 MTP 的文档治理为默认范式，用于让新仓库快速复现你惯用的 Mo's 治理形状。它定义文件角色、入口、命名和责任，不定义目标仓库的产品内容。个人默认治理语言是简体中文：ADR、Research 主题和普通文件名必须使用中文；类别代号、编号、协议名、库名、产品名、API 名等专有名词可以保留原文。

## 根目录角色

| 路径 | 默认动作 | 最低内容 |
| --- | --- | --- |
| `README.md` | 保留并补强 | 项目定位、运行入口、当前状态、Docs/Agent 入口 |
| `AGENTS.md` | 新建或补强 | 硬约束、开工阅读顺序、Skill 路由、验证和人工关口 |
| `CONTEXT.md` | 新建或补强 | 术语、领域对象、模块边界、不可混淆概念 |
| `.gitignore` | 保留并补强 | 本地 `.scratch`、验证原始物、运行状态和密钥边界 |
| `CHANGELOG.md` | 按项目需要建立 | 版本事实和变更记录 |
| `CHANGELOG.txt` | 已有双格式时同步建立 | 面向纯文本/发布入口的精简记录 |
| `LICENSE` | 只保留或等待负责人补充 | 不能猜测版权主体、许可证或年份 |

`README.md`、`AGENTS.md`、`CONTEXT.md` 和 `.gitignore` 是治理骨架的核心。版本记录和许可证按仓库发布方式处理；缺少授权信息时只记录阻塞，不伪造内容。

## Docs 目录

```text
Docs/
├── README.md
├── 当前决策/README.md
├── ADR/README.md
├── Research/README.md
├── 工作流/README.md
├── 工作流/文档治理与手动交接.md
├── 工作流/Skill协作工作流.md       # 采用多 Skill 路由时建立
├── agents/领域约定.md
├── agents/票据管理规范.md           # 采用本地票据/工作台时建立
├── 验证反馈/README.md
├── 待办与预案/README.md
├── 设计资产/README.md
├── 使用手册/README.md             # 有重复操作或人工验收时启用
├── 历史规格/README.md
├── 归档/README.md
├── 迁移与记录/README.md
└── 参考资料/README.md
```

`records/`、`plans/`、`meetings/` 是 MTP 默认骨架之外的可选扩展；是否建立按 [复现清单](reproduction-manifest.md) 判定。

完整模式应建立上述核心入口文件；扩展模块按 [复现清单](reproduction-manifest.md) 判定，需要预留的模块用 README 写明“未启用”和启用条件。不适用模块直接在初始化清单注明，不为它创建目录。`README.md`、`AGENTS.md`、`CONTEXT.md`、`CHANGELOG.md`、`CHANGELOG.txt`、`LICENSE` 等工具约定入口保留固定名称；新增普通文档用中文名称。已有 `agents/domain.md`、`agents/issue-tracker.md` 等路径保留并登记，不因语言规则擅自迁移。

如果仓库有多个可独立维护的产品域或维护域，在 `Docs/` 或 `docs/` 下增加领域入口。若按来源或维护者分区，必须注明这条轴；目录名不能自行证明作者，初始来源与当前维护责任分别登记：

```text
docs/<产品域>/
├── README.md
├── 规格/
├── ADR/
├── 架构与设计/
├── 问题与记录/
└── 验收与发布/
```

领域目录名、子目录名和文件名仍遵守中文规则；只有产品名、平台名、库名等专有名词保留原文。根文档入口必须链接每个领域 README，并说明领域文档与全局当前决策、Research、票据的关系。

## 每个入口的最低契约

### `Docs/README.md`

必须链接：当前决策、ADR、Research、工作流、Agent 约定、执行台账/`.scratch`、验证反馈和历史边界。它是读者的导航，不复制各目录的实时状态。

### `当前决策/`

保存已经确认、当前可执行的范围、决策汇总和实施顺序。`README.md` 列出主来源和状态；未确认提案不能伪装成当前决定。

### `records/` 与 `plans/`

这是 MTP 默认骨架之外的正式记录层可选扩展，不与票据混用：

- `records/` 保存决策总表、决策落点索引、未定事项表和待办表；它们记录治理事实和责任，不复制 ADR/规格正文。
- `plans/` 保存阶段计划、角色分工、首期任务计划和期限；计划说明目标与责任，不替代单票 Checklist 或当前决策主来源。
- 记录和计划文件名使用中文主题，可用日期或稳定编号追踪，例如 `001-公司筹办决策总表-2026-08-12.md`、`001-创始团队分工与首期任务计划-2026-08-12.md`。
- 待办表只登记已确定方向的执行工作；仍需选择或外部确认的内容进入未定事项表，不伪装成已授权票据。

### `ADR/`

保存难逆转、未来读者会疑惑且有明确取舍的架构/产品决策。`README.md` 说明编号制度、状态和当前决策入口；普通 UI 细节不强行写 ADR。文件名固定采用中文主题：

```text
ADR-{三位序号}-{中文决定主题}.md
```

示例：

```text
ADR-001-平台核心与Windows集成隔离.md
ADR-002-采用独立Broker作为接入服务通信边界.md
ADR-003-内容名与精灵图绑定采用三恒等原则.md
```

其中 `Windows`、`Broker` 属于专有名词；“平台核心与”“采用”“作为”“内容名与”等普通语义必须中文。ADR 主题应写成已作出的决定，不写成“方案比较”“待研究”或英文标题。

### `Research/`

保存一次性事实调查的任务书和报告。研究命名是这套治理体系的核心机制：文件名首先表达“研究对象属于哪个本地类别”，再表达“该类别中的稳定序号”，最后用中文说明“研究主题”。先从仓库实际研究对象建立本地前缀，例如平台边界、领域引擎、数据格式、代码审计、生态比较或交互研究；不要自动采用 `ENG/CODE/ECO/ARC/UX`。每个类别必须写：适用对象、反例边界、编号规则、任务书/报告配对规则、中文主题规则、交付/审阅/采纳状态和更新责任。

#### 命名规则

```text
{类别代号}-{三位序号}-{中文主题}.md
{类别代号}-{三位序号}-{中文主题}-任务书.md
```

类别代号是结构化标识，可以是 `SYS`、`CODE`、`DATA` 等稳定短码，也可以是项目决定的中文短码；它必须在 `Research/README.md` 的类别表中定义，不能临时按文件作者或版本发明。主题部分和普通文件名必须是中文；只有产品名、平台名、库名、协议名、API 名、代码符号、版本标识等专有名词保留原文。不要把普通英文形容词或 `research`、`report`、`task`、`decision`、`final` 等通用英文词混入主题或文件后缀。“调研”“审计”“审查”等可作为中文主题的一部分，不统一强加“调研”后缀。

序号在类别内独立递增：核对现有文件、索引、已预留和历史迁出编号，取该类别已分配最大序号加一；不因删除或迁移复用旧号，不按版本、讨论轮次或 Agent 名称编号。任务书和报告必须共用类别、序号和主题；有报告但没有任务书的历史材料不补造空任务书。新制度先约束新文件，历史名称通过迁移索引解释，不为整齐强制重命名。多个 Agent 建票或研究时，由统一接收者登记编号，不能各自扫描后同时占用同号。

类别重叠时按主要研究问题选择一个类别，其他领域在索引加标签或关联研究，不为同一研究重复分配编号。例如调查 Windows 合成机制属 `SYS`；只读核对某仓库如何调用相关 API 属 `CODE`；比较多条路线并给出架构建议才可能属本地定义的 `ARC`。缺少足够仓库事实时先登记“分类待确认”，不编造研究对象，也不强凑每类两个问题。

每个类别在 `Research/README.md` 中至少登记：

| 字段 | 要求 |
| --- | --- |
| 类别代号与中文名称 | 说明研究对象和允许范围 |
| 正例 | 目标仓库中真实存在的问题及路径依据；不足两个时如实登记 |
| 反例 | 明确哪些问题应该进入 ADR、当前决策、工作流或验证反馈 |
| 编号范围 | 当前最大号、下一号和历史例外 |
| 交付关系 | 是否要求任务书/报告配对 |
| 状态责任 | 谁登记交付、审阅和采纳 |

#### 完整示例

假设一个 Windows 任务栏平台仓库实际存在四类研究对象，Research 入口可以这样定义：

| 类别 | 中文名称 | 正例 | 不属于 |
| --- | --- | --- | --- |
| `SYS` | 系统与集成研究 | WinUI、Win32、任务栏、DPI、Explorer 互操作 | 已作出的宿主架构决定（进入 ADR） |
| `CODE` | 项目与参考代码研究 | 本仓库、接入应用和参考项目源码审计 | 外部库横向比较（进入 ECO） |
| `ECO` | 生态与竞品研究 | 外部工具、库、官方资料和竞品 | 本仓库实现事实（进入 CODE） |
| `UX` | 交互与原型研究 | 用户流程、浮窗交互和原型可用性 | 已确认的交互规则（进入当前决策/规格） |

对应文件名：

```text
Docs/Research/SYS-001-WinUI窗口透明合成与透明度丢失机制调研-任务书.md
Docs/Research/SYS-001-WinUI窗口透明合成与透明度丢失机制调研.md
Docs/Research/CODE-001-接入应用浮窗生命周期代码审计.md
Docs/Research/ECO-001-PowerToys宿主管理与模块生命周期调研.md
Docs/Research/UX-001-实时活动浮窗信息层级原型调研.md
```

这里 `WinUI`、`PowerToys` 是专有名词；“窗口透明合成与透明度丢失机制”“宿主管理与模块生命周期”“实时活动浮窗信息层级原型”等主题语义均为中文。`SYS-001` 的报告已交付，不代表已审阅或采纳；如果只有部分结论进入正式规格，索引应链接具体决策落点，而不是把整份报告标为“已采纳”。

另一个数据工具仓库可以本地化为：

```text
DATA-001-配置文件兼容性与迁移规则调研.md
DATA-002-批量导入错误恢复策略调研-任务书.md
```

这说明类别来自目标仓库，而不是从 MoMA/MTP 复制。

已有历史文件不为整齐而强制重命名；新制度先落地，迁移另行记录。报告已交付不等于已审阅，已审阅不等于已采纳，部分采纳必须链接具体决定。建议沿用三列事实：交付使用“未开始/进行中/已交付”，审阅使用“待审阅/已审阅”，采纳单独写“未采纳/部分采纳/已采纳/仅参考”等处置；不要用一个“完成”替代它们。

例如同一研究的生命周期如下（状态行只说明示例，不生成占位报告或虚构决定）：

| 时点 | 任务书/报告 | 交付 | 审阅 | 采纳与落点 |
| --- | --- | --- | --- | --- |
| 编制任务书 | `DATA-002-批量导入错误恢复策略调研-任务书.md` | 未开始 | — | — |
| 经授权派发 | 同上 | 进行中 | — | — |
| 收到报告 | `DATA-002-批量导入错误恢复策略调研.md` | 已交付 | 待审阅 | 未确认 |
| 维护者审阅并确认部分建议 | 同一报告 | 已交付 | 已审阅（记录日期和确认人） | 部分采纳：仅错误分类规则，链接具体规格/ADR；恢复机制建议继续待定 |

Research 索引维护当前状态，任务书和报告只保留带日期的历史快照并链接索引。任务书编制者登记编号，报告作者或接收者登记交付，维护者登记审阅，决策同步者根据确认记录登记采纳范围。附件、汇总和行动预案注明来源研究和产物类型；新报告不自动废弃旧报告，派生预案的行动状态在预案入口维护。

### `工作流/`

保存长期反复执行的开发、调研、验证、发布和交接流程。至少写清输入、输出、责任人、状态和人工确认门。文档治理文件必须规定唯一主来源、派生引用、历史材料、私有材料和交接包边界。

### `agents/`

保存领域约定、票据字段、工作台和外部 Agent 交接规则。`AGENTS.md` 只放短而硬的可执行规则，详细模板和解释放在这里或 `Docs/工作流/`。

## `AGENTS.md` Skill 工作流参考段落

下面这段是个人惯用路由的可复制参考。初始化新仓库时直接放进 `AGENTS.md` 的“Skill 工作流”小节，再补项目自己的实现、测试和真实环境要求；不要把它改成所有 Skill 必须顺序执行的流水线。

```markdown
## Skill 工作流

- 新功能、边界或架构尚未收敛：使用 `grilling` 或 `think`；关键事实无法快速确认时使用 `research-brief` / `research`；复杂交互需要体验时使用 `interaction-prototype-to-spec`。
- 已确认结论：使用 `decision-to-spec` 同步术语表、当前决策、ADR、规格或规划；需要完整阶段规划时使用 `think`。
- 用户明确授权实施：优先使用 `tdd` 或项目等价实现流程；实现完成后用 `evidence-based-validation`，阶段或版本用 `phase-acceptance`。
- 报错、回归、失败测试或行为异常：直接使用 `hunt` 或 `diagnosing-bugs`，修复后重新验证。
- 文档迁移、断链、旧路径、索引或状态一致性：使用 `docs-integrity-audit`；已确认决定缺少正式落点时再使用 `decision-to-spec`。
- UI 方向未定时使用 `frontend-design`；用户确认方向并明确要求实现时使用 `ui`；需要快速验证状态或交互逻辑时使用 `prototype`。
- 合并前审查 diff、PR 或发布准备：使用 `check`；固定基线的 Standards/Spec 双轴审查使用 `code-review`。
- 准备记录版本：使用 `changelog-writer`；创建、改造或评测 Skill：使用 `skill-creator`；Agent 指令、配置、MCP 或验证面出现漂移：使用 `health`。
- Skill 工作流或流程图更新：使用 `skill-workflow-visualizer` 依据当前 Skill 正文核对；需要重编排时使用 `skill-workflow-orchestrator`，文字规则优先于图示。
- 仓库文档首次建立或治理骨架缺失：使用 `repository-docs-bootstrap`；已有体系只查断链和状态时使用 `docs-integrity-audit`。

### 人工确认关口

- 调研任务书创建后，不自动派发或把研究建议写成正式决定。
- 原型完成后，等待用户体验并确认交互规则。
- 未通过真实设备、生产前环境或必要权限验证的能力，不得宣称已兼容或已上线。
- 用户未明确授权实现时，不从规划或研究直接进入生产代码。
- 版本号、更新日志内容、暂存范围、提交和推送必须由变更负责人确认。
```

项目必须把自身的硬约束、测试命令、平台人工验收和权限边界写在这段之后；通用路由不替代项目规则。

### `验证反馈/`

保存真实运行的原始输入、报告、人工研判或可追溯摘要。测试输出、离屏截图、沙箱、真机和生产证据必须区分，摘要不能冒充原始证据。

### `历史规格/`、`归档/`、`迁移与记录/`

分别表示已完成版本的旧规格、废弃/不再作为当前依据的材料、以及路径/索引/治理变更记录。历史材料保留追溯价值，但不能出现在当前入口的同等权威位置。

## `.scratch` 工作台

当项目需要本地票据或不公开的执行材料时，采用 [复现清单](reproduction-manifest.md#scratch-票据工作台清单) 中的期次/功能目录结构。单期票据、证据和工作文件放同一期目录，不同时维护根级与期次级两套活跃入口。跨期缓存按需采用：

```text
.scratch/
├── README.md
├── <期次或功能主题>/  # README、issues、evidence、work 和按需 goals
├── research/         # 跨期调研缓存
├── tool-cache/       # 本机工具缓存
├── 证据二进制池/      # 有大型证据复用需要时启用
└── 文档治理/          # 迁移、去重和布局核查
```

这些路径默认加入 `.gitignore`，但具体公开边界以项目规则为准。`.scratch` 不替代当前决策、ADR、Research 正式索引或规格；正式文档只链接必要的执行证据。

票据的具体头部、状态和证据规则见 [ticket-governance.md](ticket-governance.md)。不要只创建 `issues/` 目录而省略这套契约。

## 跨项目可复用结构

这套个人治理体系在不同仓库中有三种互补层次，初始化时按项目需要组合：

| 来源模式 | 可复用机制 | 新仓库中的落点 |
| --- | --- | --- |
| MTP（默认范式） | 根文件、`Docs` 当前决策/Research/工作流/验证反馈/Agent 约定、私有 `.scratch`、期次票据和分层证据 | `Docs/当前决策/`、`Docs/Research/`、`Docs/工作流/`、`Docs/验证反馈/`、`.scratch/<版本或主题>/issues/`、`evidence/`、`work/` |
| LICO（补充机制） | `records` 保存决策总表、未定事项和待办；`plans` 保存阶段计划；`adr` 与 `research` 分开 | 目标仓库确有正式记录需求时再建立对应扩展 |
| Eternal Shrine（补充机制） | 按来源和维护责任分区，分别导航规格、ADR、设计、问题、验收与发布 | 目标仓库确有多个产品域或维护域时再建立，并声明分区轴和来源依据 |
| MTP.NET 原型记录 | 在一个验证记录中分开结论、已执行验证、证据层级、已知限制和后续项；真实 Windows 结果不扩张为完整兼容承诺 | `Docs/验证反馈/` 或产品域 `验收与发布/`，链接对应票据和正式主来源 |

不要强行同时复制三套目录。先判断仓库是否有多个产品域、是否需要正式决策登记、是否需要私有票据，再选择对应层；但“正式文档、票据、证据、历史材料分离”和“每类材料只有一个当前主来源”是共同不变量。

## 初始化报告

完整模式写入一份短报告，至少包含：

- 基线版本和生成日期；
- 根文件与 Docs 入口的保留/补强/新建/不适用状态；
- 本地研究分类及其证据、反例边界和编号起点；
- 唯一主来源矩阵；
- 未启用目录、未决命名、负责人待补充项和后续维护责任；
- 静态链接检查范围以及未检查的真实环境/人工项目。
