# 证据驱动验证

这个 Skill 是一张针对单个改动的“验证卡”，不是小规模阶段验收。它只回答“这个改动的目标行为有没有被正确证明”：单元测试擅长证明逻辑，离屏测试能覆盖部分 UI 结构，真实系统/设备/沙箱才能证明原生交互、权限和环境配置。没有对应环境时，明确未证实的边界，并给出别人可以照做的人工验证步骤。

## 完成条件与上下文摘要

- 维护参考：`skills/_shared/references/work-item-contract.md`、`skills/_shared/references/evidence-status.md`、`skills/_shared/references/confirmation-gates.md`。
- 完成条件：目标行为的必需证据已执行，或缺失环境已明确标为 `待人工`/`阻塞`，且没有把低层结果扩大成高层结论。
- 同一上下文中的后续验收直接复用当前证据；只有跨 Agent、跨会话或长期留档时，才摘要目标、环境、命令、证据、覆盖范围、未决问题和下一步。
- 多个改动组成阶段时，把验证卡交给 `phase-acceptance`；发现明确故障根因问题时，再交给 `hunt`。

## 操作边界

- 服务于一次具体的改动、修复或待确认行为。先定位该行为的控制代码、约束和现有测试；不要汇总多个交付承诺，也不要给阶段或版本下“可交付”结论。
- 本 Skill 负责选择验证层、组织证据和判断覆盖边界。代码审查、浏览器自动化和项目测试优先交给上游 `check`、`code-review`、`webapp-testing` 或仓库已有命令，不重复实现这些执行能力。
- 先遵循仓库的项目指令、测试说明和现有脚本。项目要求真实环境验证时，不能用本地替代并声称通过。
- 默认执行非破坏验证：读取、已有测试/构建/检查、无状态冒烟、临时 probe。运行前后检查工作区状态。
- 测试、构建和 probe 可能生成缓存、日志、截图和产物。只清理由本轮明确创建且确认无用户内容的临时文件；遇到不明改动只记录，不删除。
- 不修改业务代码、不创建 issue、不提交或推送，除非用户明确把任务转为修复、登记或发布。
- 无终端、真机、沙箱、账号或权限时，停止假装验证，改交付可执行的人工清单和受限原因。

## 工作流程

### 1. 定义可证伪的验证目标

先读用户描述、附近实现、相关测试和项目规则，写清：

- 改动后的可观察行为；
- 关键入口和操作；
- 失败会造成的影响；
- 不能由低层测试证明的部分；
- 已有命令、测试和环境限制。

把“代码存在”“命令退出 0”和“用户能完成流程”分开。验证目标应能被结果推翻，例如“目标操作系统的原生样式下，下拉箭头的点击区域会打开菜单”，而不是“下拉框看起来正常”。

### 2. 选择最低但足够的验证层

本 Skill 只决定“需要什么证据”，不重复实现执行器。按目标选择证据来源：

| 风险或行为 | 证据来源 | 不能替代它的证据 |
| --- | --- | --- |
| 纯逻辑、解析、状态转换 | 项目专项单元/集成测试 | 代码阅读、构建成功 |
| CLI 输出、文件结构、浏览器交互 | 实际命令、`webapp-testing` 或人工流程 | 只断言内部函数 |
| UI 结构与视觉 | 离屏检查、截图或上游 UI 工具 | 纯逻辑测试 |
| 原生控件、云端权限、发布迁移 | 目标环境 probe、沙箱/预发布演练和人工证据 | offscreen、mock、本地构建 |

代码审查交给 `check` 或 `code-review`，浏览器交互交给 `webapp-testing`，专项测试交给项目已有命令。一个目标需要多个层级时分别记录；低层通过只能缩小故障范围，不能把高层标成通过。

### 3. 制定最小验证计划

复用上游执行器和项目已有命令，列出每项检查的：

| 验证项 | 层级 | 操作或命令 | 通过标准 | 证据 | 失败时保留 |
| --- | --- | --- | --- | --- |

只在现有执行器覆盖不到关键风险时提出最小 probe；probe 只暴露需要确认的观测值，不把临时诊断变成长期开关。开始前确认：

1. 目标环境是否真的可用；
2. 命令会产生什么文件或写入；
3. 哪些结果要截图、复制日志或记录路径；
4. 临时 probe 的删除条件。

### 4. 执行、记录和判读

执行每项验证并留下足够复核的原始证据：命令、环境、退出状态、关键输出、截图/日志/响应位置，以及是否覆盖了目标路径。

判读时使用以下状态：

| 状态 | 含义 |
| --- | --- |
| 通过 | 必需层级已执行，结果符合明确标准 |
| 失败 | 已执行且证据表明不符合标准 |
| 待人工 | 需要人操作、视觉/业务判断或当前没有自动化入口 |
| 阻塞 | 缺少关键环境、权限、依赖或凭据，关键结论无法获得 |
| 不适用 | 当前改动不涉及该层级，说明理由 |

跳过、过滤、空测试、命令未进入目标分支、离线 mock 或环境启动失败都不算通过。区分产品缺陷、测试缺陷、环境问题和证据不足；后一类不可写成失败，也不可写成通过。

### 5. 给无法自动化的项写人工步骤

不要写“请手动测一下”。每条人工项都按以下格式交付：

```markdown
#### [验证目标]
- 环境：
- 前置条件：
- 操作：
- 预期：
- 失败时保留：截图、日志、响应内容或复现条件中的具体内容。
```

对原生 UI 明确操作系统、缩放和窗口状态；对云端流程明确账号角色、隔离环境和禁止触碰的真实数据；对发布/迁移明确备份、回滚点和授权边界。

### 6. 输出验证记录

- 输出至少包含稳定的改动标识、目标行为、验证命令、执行环境、证据位置、已覆盖范围、未覆盖边界和最终状态，供 `phase-acceptance` 汇总时复用。阶段验收不应因已有验证卡而重复运行相同检查，除非代码、环境或证据已经变化。
优先写入项目已有的验证反馈或测试记录目录。路径不明确、报告公开范围不明或没有写入权限时，在对话中完整输出报告，并说明建议路径及未落盘原因。

使用以下模板：

```markdown
# [改动或行为] 验证记录

## 结论
- 总状态：通过 / 部分通过 / 不通过 / 阻塞
- 已执行：X 项通过，X 项失败
- 待人工：X 项
- 阻塞：X 项
- 证据边界：哪些结论已由何种环境证明，哪些尚未证明。

## 验证目标与计划
| 验证项 | 层级 | 操作或命令 | 通过标准 | 状态 | 证据 |
| --- | --- | --- | --- | --- | --- |

## 执行记录
### [验证项]
- 环境：
- 实际操作：
- 结果：
- 原始证据：
- 覆盖边界：

## 待人工与阻塞项
#### [验证目标]
- 环境：
- 前置条件：
- 操作：
- 预期：
- 失败时保留：
- 阻塞原因或未证实边界：

## 验证副作用与清理
- 本轮生成：
- 已清理：
- 未清理及原因：

## 后续动作
1. [最优先的修复、复验或人工动作]
```

总状态规则：所有关键目标已由其必需层级证明时为“通过”；关键逻辑已通过但仍有不阻塞人工体验项时为“部分通过”；关键验证失败时为“不通过”；缺少关键环境导致核心目标无法判断时为“阻塞”。

## 与相邻 Skill 的边界

- 用 `phase-acceptance` 在阶段或版本结束时汇总多项承诺和验收结论；本 Skill 为一项具体改动设计正确证据。
- 用 `hunt` 查找已知故障的根因；本 Skill 在修复后证明行为是否真的恢复。
- 用 `check` 审查 PR、代码质量和发布准备；本 Skill 不评审设计优劣或提交质量。
- 用 `qa` 记录人工发现的问题；本 Skill 只记录验证证据，除非用户要求创建 issue。

## 常见误判

- 测试套件通过不证明真实原生控件热区、缩放和窗口装饰正确。
- 本地 mock 成功不证明云端权限、回调地址和环境变量正确。
- 构建成功不证明发布物被部署、可访问或可回滚。
- 没有截图不等于没有证据；但涉及视觉和交互时，日志通常也不足以替代截图或人工操作。
- 无法执行的高层验证应是“待人工”或“阻塞”，不是“低层已通过所以整体通过”。
