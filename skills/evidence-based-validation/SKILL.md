# 证据驱动验证

回答“这个改动的目标行为是否得到证明”。核心产物是目标与证据的对应关系；能用几行说明的小改动不必扩成报告。

## 1. 明确目标与已有证据

读取具体改动、控制路径、相关测试和项目规则，把目标写成可被结果推翻的行为。例如“目标系统中点击下拉箭头能打开菜单”，而不是“控件正常”。

先判断现有结果是否覆盖当前代码、环境和目标。能够复用就直接复用；仅命令相同、结果很新或测试全绿都不能证明覆盖有效。用户只是要运行明确命令且没有覆盖疑问时直接执行，无需验证卡。

范围限于该改动，不扩展为版本可交付结论。只读、既有测试、构建、无状态冒烟和临时 probe 可按任务授权执行；不借验证修改业务代码、运行时数据、云端资源、创建 issue 或执行 Git 写操作。探针需要改产品代码或触及外部状态时，先准备方案并核对已有授权。

## 2. 选择最低但足够的证据

| 目标 | 通常需要的证据 | 不能代替它的结果 |
| --- | --- | --- |
| 纯逻辑、解析、状态转换 | 专项单元或集成测试 | 代码存在、构建成功 |
| CLI、文件产物、浏览器操作 | 实际命令/产物/操作路径 | 仅内部函数断言 |
| 视觉与 UI 结构 | 对应视口的截图、离屏检查或实际界面 | 纯逻辑测试 |
| 原生交互、云端权限、迁移或部署 | 目标环境运行、合适账号/数据的演练与观测 | mock、offscreen、本地构建 |

实际要求以目标和项目规则为准，不把表格当成必须全部执行的层级清单。一个目标需要多层证据时分别记录。

优先直接使用项目已有命令；只有需要审查或浏览器能力时再用可用的 `check`、`code-review`、`webapp-testing` 或等价执行器。不因提到了测试就串联所有 Skill，也不重复执行已有充分证据。

列出最少的“检查 → 命令/操作 → 环境 → 通过标准 → 证据”。区分目标必需证据和补充体验项；不能为了获得通过而把原本必需的检查降为可选。

## 3. 执行与判读

执行前后检查工作区；预先了解命令的写入和产物。只清理由本轮明确创建且无用户内容的临时文件，不删除来源不明的变更。

保留足够复核的命令或操作、环境、退出状态、关键输出和日志/截图/响应位置。退出码须按实际工具约定判读；跳过、过滤、空测试、未进入目标路径或环境启动失败不能算通过。

| 结果 | 含义 |
| --- | --- |
| `passed` / 通过 | 实际覆盖目标，证据满足标准 |
| `failed` / 失败 | 已有证据表明目标不符合标准 |
| `manual` / 待人工 | 需要人工操作或判断，尚未完成 |
| `blocked` / 阻塞 | 必需环境、权限或依赖缺失，无法判定 |
| `not-applicable` / 不适用 | 不涉及此目标，写明依据 |

区分产品失败、测试自身故障和环境问题。测试故障使目标无法判断时，记录该故障与证据缺口，不冒充产品失败或通过。其他证据不足项可记为待核实，不硬塞成已通过结果。

## 4. 交付最小验证卡

每项保留五个可供后续验收复用的字段：**证据位置、环境、结果、覆盖、未覆盖**；并标明改动标识和目标。无需固定标题，简单结果可用紧凑表格。

单改动结论按必需证据判断：已有目标失败则不通过；无失败但缺关键条件则阻塞；其余必需人工或待核实项尚未完成则部分通过；所有必需目标已证明才通过。非必需体验项保留为后续，不单独降低结论；它若暴露违反必需标准的问题，仍算失败。

人工项写清“环境/前置条件 → 入口与动作 → 可观察预期 → 失败时保留什么”。原生界面按需注明系统、缩放和窗口状态；云端注明账号角色与隔离数据；迁移注明备份与回滚点。不要只写“请手动测一下”。

默认在对话中交付。用户要求保存或项目规则指定验证记录时，沿用项目位置，否则用 `.scratch/reports/evidence-based-validation/<YYYY-MM-DD>-<改动标识>.md`。补充实际副作用及未清理原因即可，不为不存在的内容创建空章节。

阶段结束时将当前证据交给 `phase-acceptance`，无需另造交接表；跨会话时补上改动版本、证据位置和剩余动作。发现明确故障可建议根因排查，只有用户已授权修复时才转入修复。
