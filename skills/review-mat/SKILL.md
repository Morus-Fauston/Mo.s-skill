# MAT 统一审阅：判断明确版本的交付是否成立

基于 Matt Pocock 的 `code-review` 方法改写；改动和许可见 [UPSTREAM.md](<UPSTREAM.md>)。该说明仅供来源追溯，不是执行前置。

交付可追溯的审阅意见：审了什么、依据什么、哪里有问题、还有哪些无法判断。规范符合不保证满足需求，需求满足也不代表证据足够；不能用一个“通过”掩盖另一项缺口。

## 1. 锁定审阅对象与责任

从系统记录确认真实角色、会话、当前任务、送审关联、作者及独立性。不要把角色名称、正文自报、API 的 `user` 角色或“换个帽子看”当成正式审阅资格。

| 本次责任 | 可以交付什么 |
|---|---|
| 作者自查、辅助核对、主管查核 | 发现、证据、局限及建议；不调用正式意见入口假装独审 |
| 系统指定的非作者独立审阅会话 | 在实际授权和送审范围内提交正式通过／退回意见 |

角色规范复用已保存来源，空正文合法；必需身份、规范或工作依据真正缺失时报告，不临时猜写。当前授权和资料充分就直接核对，不另申请同一范围；缺必要人类判断时走管理入口，不能自己代答。

- 读取当前要求、范围／非目标、验收条件、Checklist、交付简报、必要证据及相关项目规范。复审再取得原意见与修改依据，不复制作者整段上下文。
- 固定本次成果及基线的可追溯身份：可以是已提交差异、未提交成果、报告版本或项目提供的等效记录。**不强制先 commit，不固定使用 `HEAD...` 比较**；按实际交付核对已暂存、未暂存、未跟踪、删除及重命名的相关内容。
- 共享目录可能继续变化，读取到的文件必须与送审对象对应。无法对应时只报告可以确认的部分，要求恢复明确版本，不拿当前文件替旧证据背书。没有代码 diff 不等于报告或混合交付为空。
- 规格缺失不能凭实现猜需求；可完成独立的规范／质量核对，但需求轴标为无法判断，不以“未发现问题”放行未覆盖范围。

## 2. 按对象检查，始终区分两个角度

### 代码：规范符合度与需求符合度

**规范轴**：核项目明确的编码／接口约束、相关质量、测试可维护性和变更对旧成果的影响。工具已可靠检查的内容可引用适用结果，不再机械重复。

没有特别规范时，以下是质量线索，不是自动判违规的规则：含混命名、重复代码、职责分散、过长转发链、为了假想需求造抽象、相同条件分支反复出现、相关数据总成组传递、领域概念只用无约束字符串表达。将发现关联实际行为或修改成本，标为判断性建议；项目明确的例外优先，不为凑数量挑风格问题。

**需求轴**：逐项核对本次约定的行为、异常路径、兼容性及验收条件；识别遗漏、错误实现、擅自扩围，以及无有效依据的 Checklist 勾选。对接口、依赖和已有成果有实际影响的部分补核，不每票重审全项目。

两个角度分别给结论；同一问题可以互引但不要重复计数或把一个角度的好结果抵消另一个角度的失败。

### 研究／分析报告：问题覆盖与论证依据

沿原研究问题逐项核：是否回答、证据是否支持、还缺什么。查看关键引用的原文、版本和适用条件；报告中“已验证”“据官方文档”不是原始证据。

- 区分第一手事实、第三方描述、推断和建议，保留互相矛盾的来源及解释；引用数量不能代替来源可靠性。
- 查结论是否超出样本、平台、版本或运行范围；静态源码、模拟、本机观察不能冒充真机／生产结论。
- 有依据的“仍无法确认”可以是合格研究结果，按原问题的完成标准判断；要求必须取得却未取得的证据不能悄悄降级。
- 报告审阅通过不等于建议被采纳，更不修改产品需求或授权。

### 混合成果：检查代码与文字是否相互支持

取证脚本、测试输入、结果文件和报告一起核对：脚本实际观测的对象与报告是否一致，输入与环境能否复现所称结果，报告是否遗漏失败或扩大结论。分别完成适用角度，再说明它们的关联，不把脚本编译成功当成报告结论成立。

## 3. 只补足必要证据

优先核验已有证据对应的**版本、环境、覆盖和结果**；仍适用就复用。作者说测试过、上次审阅通过、CI 全绿或命令退出零都不能单独证明当前送审版本满足要求。

必要时在自己的审计／验证材料域编写复现脚本、输入和记录，运行获准检查；不修改被审业务成果、他人材料或真实外部数据。若既有测试默认会写被审目录，先选择已有获准的隔离方式或协调，不以“只是验证”绕过写域。

- 记录实际命令／操作、环境、结果和证据入口；跳过、空测试、路径未触发、测试器故障与产品失败分开。
- 需要真机、账号或人工体验而当前没有时，给可执行的补证步骤，明确未完成；不拿 mock、离屏或静态检查代替。
- 复审仅复核原问题和修改影响范围，复用仍有效的证据，不无理由全量重审；发现影响扩大时说明依据。
- 当前会话自己完成审阅，**不创建子代理或辅助会话，也不通过其他 Skill 间接委派**。不改代码来让测试变绿、不做 Git 写操作、不安装工具、不派额外审计。

`evidence-based-validation` 负责具体证据设计与判读，`phase-acceptance` 负责阶段承诺，`docs-integrity-audit` 负责文档机械一致性。需要时使用适用方法或已有工具，不固定串成流水线，也不借转调用扩大权限。

## 4. 给出意见并按真实入口办理

先说结论及最重要问题，再列：**对象／范围／版本、规范轴与需求／问题覆盖轴的结果、问题依据和影响、修正建议、未检查项与证据缺口**。报告类按对应角度命名即可，不强塞代码风格章节。建议是解决问题的方向，不是新增需求。

- 必需要求有失败证据，或交付缺少约定的必要部分：明确退回理由，不能用其他成功项平均成通过。
- 尚无法确认关键对象、版本或必需证据：明确无法判断及所需材料；可以完成的核对仍交付，不伪造“全覆盖”。不适用项须有理由。对象与版本已明确，而交付遗漏原要求必须提供的证据时，按缺交付部分退回补证；若连送审对象、权限或版本都无法确认，则先联系责任入口恢复必要记录，不对猜测的对象提交通过或退回，不新增票据状态。
- 只有对应范围的必要检查与证据满足，才可给通过意见；说明覆盖与未覆盖，不能用“没有看到问题”代替必要检查。

正式审阅使用当前真实可见的 MAT 审阅意见入口，绑定原票、尝试和送审版本，填写实际支持的通过／退回及依据。退回沿原执行同次修正，通过仅成为**审阅通过**，不是票据已完成、提交许可或人工验收。状态与通知由该动作按 MAT 规则联动，不再另调改状态、重派审计或重复发同文 Chat。

缺业务入口时可继续已授权、控制允许的只读核对并交付“待提交意见”，但正式办理保持未完成；不直接写数据库、改票据文件、另用 tracker 或伪造送达。提交超时／结果未知先查原关联；已保存不重复提交，仍未知则保持待核实并联系实际责任入口。

本方法仅替换 MAT 中的审阅入口，不改变 MAT 外个人 `code-review`／`check`。正文与 frontmatter 不提供权限隔离；真实来源、独立性和工具授权必须由 MAT 核验。场景库不是模型执行或端到端通过记录。
