# 阶段验收

回答本阶段承诺了什么、证据证明了哪些、还缺什么以及谁来完成。交付完整验收结论；检查受阻时仍交付已知结果和可执行的剩余步骤。

## 范围与授权

遵循项目验收契约与工作区约定。默认读取、运行既有测试/构建和不写用户数据的检查；不修改产品代码、配置、运行时数据、云端资源或发布状态。测试产物与原有修改分开记录，不清理他人文件。

验收通过不自动授权发布、提交、推送或修改票据状态。修复、登记缺陷和排期仅在相应任务授权内进行。

## 1. 提取本阶段契约

读取相关规划、任务书、规格、ADR、项目指令和当前改动，只纳入本阶段已确认的承诺。每项写清：

- 行为或交付物、来源与通过标准；
- 必需性：交付所需，或非必需补充；
- 所需验证层与证据来源。

不把愿景、远期计划和未批准讨论加进本阶段。Git diff 能证明变化，但不能单独定义验收标准；契约不完整时明确缺口，只核对已有可观察事实。不能为了让总状态通过而降低必需性。

## 2. 对照已有证据，只补缺口

| 证据层 | 判读边界 |
| --- | --- |
| 自动验证 | 命令按约定成功且实际覆盖目标路径；跳过、空测试和错误过滤不算通过 |
| 静态核对 | 以真实文件、配置或调用路径为依据，不能冒充运行结果 |
| 本机交互 | 记录实际系统、视口或 CLI 路径，只证明该环境 |
| 真实环境 | 原生样式、真机、沙箱、云端或生产前环境必须在对应环境验证 |
| 人工体验 | 视觉、文案、操作感受或业务判断须有实际体验记录 |

一个验收项需要的证据层都满足才通过。离屏不能替代原生交互，本地模拟不能替代云端权限，沙箱不能替代生产配置，构建不能证明已部署。

优先复用验证卡、审查报告、浏览器检查和项目测试结果。核对其代码版本、环境与覆盖是否仍适用，仅在相关变化、失败或证据缺口出现时重跑。已有充分验证不因换了一个 Skill 再执行一轮。

补本阶段特有的跨改动集成、发行包、真实环境或人工检查。项目命令优先，需要额外能力时再使用可用的 `check`、`code-review`、`webapp-testing` 或等价工具，不强制串联。

## 3. 记录每项状态与影响

证据记录包含命令/操作、环境、实际结果、覆盖路径、原始位置及实际副作用。每项状态为“通过、失败、待人工、阻塞、不适用”；不适用需有依据。

区分产品不符合要求、测试/检查器故障和环境阻塞。未进入目标分支或无法取得结果不能写成通过。证据不足且尚不能确定原因时标注待核实，不把猜测计为失败。

发现按影响分开：

| 发现 | 处理 |
| --- | --- |
| 问题 | 用证据关联受影响验收项；违反必需标准时计为失败 |
| 待优化项 | 当前符合标准，说明为何不阻塞 |
| 建议 | 后续改进，不伪装成本阶段必需修复 |
| 待核实项 | 说明缺什么证据、如何补，不算已通过 |

## 4. 判定总状态

按以下顺序取首个满足的状态，其他失败和缺口仍逐项列出：

1. **不通过**：至少一个必需项有失败证据，或存在违反核心交付要求的问题。
2. **阻塞**：无上述失败，但缺少关键环境、权限、依赖或契约，必需项无法判断。
3. **部分通过**：无上述失败或阻塞，仍有未完成的必需人工检查或待核实项。
4. **通过**：所有必需项均通过；有依据的不适用项不计入必需项。

非必需项未完成、待人工或待核实不降低总状态，只记录后续；若补充检查发现必需标准被违反，必须关联回必需项按失败处理。结论写“必需验收项通过，另有非必需后续事项”，不能写“全部检查完成”。

## 5. 交付报告与剩余步骤

先给总状态，再列验收项、必需性、验证层、证据和状态，以及实际发现与下一责任人。没有发现的问题可合并说明“已检查且未发现”；未检查项和限制单列，不强制填空章节。

所有待人工或阻塞项都应有可复现步骤：

> 在 [环境与前置条件]，从 [入口] 执行 [动作]；预期 [可观察结果]；失败时保留 [具体截图、日志或响应]。

环境不可用时说明缺件、可用后如何验证；不能只写“请手测”。摘要可突出最重要几项，但完整报告须保留全部未完成的必需项。

默认在对话中交付 Markdown 报告。用户要求保存或项目规则已指定记录位置时，优先沿用该位置，否则用 `.scratch/reports/phase-acceptance/<YYYY-MM-DD>-<阶段名>.md`。检查私有/忽略边界，不改变公开范围；公开范围不清时先在对话中交付，仅澄清有歧义的保存动作。无写权限时仍交付完整正文与建议路径。

同一上下文直接复用报告；跨会话才补充契约、代码版本、证据位置、阻塞与下一步。报告完成代表验收工作已交付，阶段是否通过由上述证据决定。
