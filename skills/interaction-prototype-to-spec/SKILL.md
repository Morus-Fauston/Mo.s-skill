# 从交互原型到规格

复杂交互在文字里通常说不清。这个 Skill 的目标是让原型回答一个具体问题，例如“分类如何导航”“输入框什么时候展开候选”“管理员如何从查看切到编辑”，然后把已经体验并确认的行为写成开发能实现、测试能验证的规格。

## 完成条件与上下文摘要

- 维护参考：`skills/_shared/references/work-item-contract.md`、`skills/_shared/references/confirmation-gates.md`。
- 完成条件：原型问题已回答或用户明确未选择；已确认规则、否决方案、未决边界和原型证据都已记录。
- 同一上下文继续讨论时不需要固定表格；只有跨 Agent、跨会话或长期留档时，才摘要原型问题、访问位置、覆盖路径、用户决定、未决问题和下一步。
- 用户尚未体验或选择时，状态必须停在 `awaiting-user`；确认后交给 `decision-to-spec`，需要完整规格时先交给 `to-spec`。

## 操作边界

- 原型是验证问题的临时代码，不是生产实现。默认调用上游 `ui` 制作好看的可体验视觉原型；只有状态模型、权限分支或逻辑本身难以纸面判断时，才调用上游 `prototype`。
- 上游 `ui` 或 `prototype` 只负责原型执行。本 Skill 负责定义原型要回答的问题、比较真正不同的交互范式、收集用户选择并守住确认门。
- 先确认用户想回答的问题，再做原型。不要为了展示技术能力做一个漂亮但不能帮助决策的页面。
- 可以设计多个真正不同的交互范式，但不要只换颜色、字体或卡片样式就说是多个方案。
- 原型阶段不修改生产代码、不替用户做产品决定。用户体验后明确选择的规则才进入规格；需要实现生产界面时，另行由用户确认后调用上游 `ui`。
- 未选方案、被否决方案、尚未讨论的视觉细节只保留为原型/讨论记录，不得混入现行规格。
- 原型文件是否保留、归档或删除，遵循项目规则；结论和理由必须落到稳定文档，不能只留在聊天或 HTML 中。

## 工作流程

### 1. 定义原型问题和比较维度

先读取最接近的需求、现有界面、术语和约束，明确：

- 谁在什么场景下完成什么任务；
- 当前文字描述中最不确定的交互问题；
- 用户必须亲自体验才能决定的差异；
- 不能改变的技术、权限、数据或无障碍约束；
- 原型要覆盖的状态：初始、展开/收起、搜索/过滤、空态、错误、权限差异、长内容或移动端。

将问题写成可以由原型回答的一句话，例如“研究字段的内容选择器应如何同时支持大量分类浏览和双语搜索”，而不是“做一个好看的选择器”。

### 2. 设计真正不同的范式

为复杂交互给 2 到 3 个有实质区别的方案。每个方案说明：

| 方案 | 主任务路径 | 浏览方式 | 搜索方式 | 关键取舍 | 适用条件 |
| --- | --- | --- | --- | --- |

差异应来自信息架构、操作顺序、状态呈现、权限或密度，而不是配色。不要提前宣布推荐方案为定案；先指出每个方案要让用户验证的感觉或风险。

### 3. 委托制作可体验原型

根据待验证问题选择上游执行器：

| 主要问题 | 上游执行器 | 本 Skill 需要接收的结果 |
| --- | --- | --- |
| 视觉层级、布局、密度或美术方向不清 | `ui` | 可访问原型/截图、已覆盖路径、待体验状态 |
| 状态转换、权限分支或交互逻辑难以判断 | `prototype` | 可运行原型、状态覆盖、未覆盖边界、待体验状态 |
| 两者都重要 | 先 `ui`，必要时补 `prototype` | 两类覆盖范围分别记录，不把一类证据冒充另一类 |

原型执行器交付后，检查它是否提供可访问的文件或地址、已覆盖的关键路径和状态、未覆盖的生产约束，并确认当前状态仍是“待用户体验”。缺少这些信息时停在待核实，不得自动进入规格或生产实现。

交付回收时只检查原型是否覆盖会影响选择的关键路径和状态，并记录桌面/移动视口、代表性数据、权限差异、错误和空态等未覆盖边界。原型执行器负责实现和运行原型；本 Skill 不重复规定框架、组件结构、视觉规范或运行方式。原型只能证明被模拟的交互，不能证明生产代码质量、真实性能、原生控件行为或真实权限。

### 4. 收集体验结论并分流

原型完成并验证关键路径后，必须停在“待体验”状态，向用户交付可访问的原型和要比较的问题。未收到用户对具体方案、规则或取舍的明确反馈时，不得进入第 5、6 步，不得自行假设用户选择了某个方案。

将结果分为四类：

| 结果 | 处理 |
| --- | --- |
| 已确认交互规则 | 准备进入规格 |
| 明确否决方案 | 保留在原型记录或讨论记录，不进入现行规格 |
| 未决问题 | 列为待确认，不能让开发自行猜测 |
| 需要事实/可行性调研 | 转为调研任务或技术验证，不能写成确定交互 |

当用户说“和我想的不一样”时，先回到具体路径，确认是入口、触发时机、信息结构、视觉层级还是状态反馈理解错了；不要只微调颜色或间距。

### 5. 形成可开发规格

只记录已确认规则。每个规则必须包含：

| 维度 | 要写清的内容 |
| --- | --- |
| 入口 | 用户从哪里开始，哪些条件下可见/可用 |
| 状态 | 初始、展开、搜索、选中、空态、错误、禁用和关闭后的行为 |
| 操作 | 点击、键盘、输入、返回、取消、确认的结果 |
| 数据契约 | 输入、过滤、显示值、持久化值、默认值和错误处理 |
| 权限/范围 | 不同角色或上下文看到什么、能做什么 |
| 边界 | 大数据量、长文字、小屏幕、无候选、重复操作或切换上下文 |
| 验收条件 | 可观察、可测试的通过标准 |

不要把原型像素值、临时假数据、演示动画或未确认美术细节抄进规格。视觉方向另有明确决定时才落入设计规格；否则写行为，不写装饰。

### 6. 同步与交付

先读取当前项目的文档职责与命名规则，再使用 `decision-to-spec` 将定案同步到正确位置：产品行为进入需求文档，具体交互/数据/验收进入设计规格，难逆转的跨模块取舍进入架构决策记录，术语进入术语表或领域模型。原型本身可归档到项目约定的设计资产目录；被否决方案不能在当前设计入口中伪装成可选实现。

输出记录使用：

```markdown
# [交互名称] 原型结论与规格摘要

## 原型问题
- 要回答：
- 目标用户和场景：
- 未包含：

## 已体验方案
| 方案 | 验证的关键路径 | 用户结论 | 状态 |
| --- | --- | --- | --- |

## 已确认规则
| 规则 | 入口/状态 | 数据或权限边界 | 验收条件 |
| --- | --- | --- | --- |

## 未决与否决
- 待确认：
- 已否决：
- 待调研：

## 文档落点
| 文档 | 更新内容 | 原因 |
| --- | --- | --- |

## 开发前仍需确认
- [具体问题或写“无”]
```

若无法写文件，在对话中完整输出同一记录和建议路径。交付时先说明“原型证明了什么、没有证明什么”，再列出已确认规则与仍不可直接开发的事项。

## 与相邻 Skill 的边界

- 用 `prototype` 制作 throwaway 原型；本 Skill 决定原型该问什么，以及如何把结论变成规格。
- 用 `ui` 制作生产级视觉界面或改善现有 UI；本 Skill 不把原型直接升级为生产界面。
- 用 `grill-with-docs` 追问仍未确定的产品分歧；本 Skill 不代替用户拍板。
- 用 `decision-to-spec` 同步已确认结论；本 Skill 提供决策清单和交互契约。
- 用 `phase-acceptance` 验收生产实现；原型通过不等于生产功能通过。

## 常见误判

- 原型能点击，不等于真实权限、性能、原生行为或数据一致性已验证。
- 原型展示了三种方案，不等于三个方案都可开发；要记录被否决的理由。
- 用户认可整体感觉，不等于每个状态和数据边界都已确认。
- 原型中的占位内容不应成为正式数据模型或文案。
- 原型页面存在不等于规格已完成；没有入口、状态、数据契约和验收条件，开发仍会猜。
