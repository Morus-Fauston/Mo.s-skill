# 从交互原型到规格

用可体验原型回答具体交互问题，再把用户确认的行为整理成开发和测试都能使用的契约。尚未选择时交付原型并停在 `awaiting-user`；已确认时交付规则、证据边界和正式文档落点。

## 1. 找到需要体验的问题

读取相关需求、现有界面、术语和约束。确定谁在什么场景完成什么任务、哪一段操作还拿不准，以及不能改变的权限、数据或技术边界。用户已说明问题时直接沿用，不重新采访。

把原型问题写成能验证的一句话，例如“分类浏览与双语搜索怎样协同”。只覆盖影响这个选择的路径和状态；不要为了原型完整而补出整套产品。

若原型结论已经明确，只需落盘，直接进入规则整理和 `decision-to-spec`，无需再做原型。

## 2. 选择最小有效原型

方案数量服从待决问题与用户要求。存在真实分歧时，比较信息架构、操作顺序、状态反馈或权限路径不同的方案；仅需验证一个已选方向时，一个原型即可，不强制凑 2 到 3 套。

按问题选择执行方式：

| 需要回答的问题 | 执行方式 |
| --- | --- |
| 布局、视觉层级、密度、入口是否易懂 | 优先使用可用的 `ui` 或项目等价界面工具 |
| 状态转换、取消/重试、并发、权限切换的行为必须运行才能判断 | 使用可用的 `prototype` 或最小可运行模拟 |
| 同时涉及视觉与状态 | 尽量由同一个原型覆盖，按缺口补验证，不机械串行调用两个 Skill |

状态数量、角色数量和异步过程是风险线索，不是强制启用 `prototype` 的阈值。即使有四个状态，若问题只是菜单位置，视觉原型可能足够；两个状态间的异步竞争也可能需要可运行模拟。工具不可用时使用已授权的等价方式，并说明限制，不把工具名称当作交付结果。

原型代码放在项目约定的临时或设计资产目录，保持与生产实现分离。不把假数据、演示权限、像素值或临时动画自动升级为正式要求。

## 3. 验证路径并交给用户体验

检查原型是否可访问，实际走过影响选择的关键路径，记录覆盖的视口、代表性数据、空态、错误或权限分支，以及未模拟的生产约束。只验证与问题有关的内容，不复写执行器的框架和组件规范。

交付访问位置、比较问题和已知限制，然后等待用户对具体方案或规则的反馈。原型只能证明模拟过的交互，不能证明生产性能、真实权限、原生控件或数据一致性。

- 用户尚未体验或选择：停在 `awaiting-user`，不写现行规格、不实现生产代码。
- 用户说“和想的不一样”：定位入口、触发时机、信息结构或反馈中哪一段不符，再调整。
- 用户认可整体感觉：只记录其确实确认的部分，不能推断所有异常边界都获准。
- 已有明确体验结论：复用它，不重复设置确认门。

## 4. 整理已确认交互契约

按规则实际涉及的维度写清：入口与可用条件、状态转换、操作结果、显示值与持久化值、权限/数据边界、异常行为和可观察的验收条件。无关维度可省略；未决边界明确标注，不让开发自行猜测。

把已确认规则、明确否决方案、未决问题和待调研事实分开。需要完整功能规格时使用项目规格流程；已有完整规格时只补本次规则。

通过 `decision-to-spec` 或项目等价文档流程同步：行为与验收进规格，术语进领域文档，存在实质取舍的决定进 ADR。被否决方案保留为历史依据，不放在当前入口中冒充可选实现。已有用户授权覆盖这次同步时直接执行。

## 5. 交付与保存

先说明原型证明了什么，再列已确认规则、正式文档位置和仍不能直接开发的边界。跨会话才增加问题、覆盖路径、用户决定和下一步摘要。

默认不另建**原型总结报告**；这不限制原型文件和已获授权的正式文档更新。用户要求报告或需保存交接材料时，优先沿用项目设计资产目录，否则用 `.scratch/reports/interaction-prototype-to-spec/<YYYY-MM-DD>-<交互名称>.md`，保留问题、方案结论、规则、未决项和文档落点即可。

原型的保留或归档遵循项目规则，不自行删除用户资产。生产实现和生产验收需有相应任务授权，原型通过不能替代它们。
