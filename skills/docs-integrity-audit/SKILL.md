# 文档完整性审计

找出会误导读者或 Agent 的入口失效、旧规则残留、状态漂移和重复权威来源。结论须能指向实际文件与检查范围，不能把相似文档或历史路径自动判为缺陷。

## 1. 建立审计范围

读取项目指令、README、文档入口和与用户目标相关的目录，区分现行术语、ADR、需求/规格/规划、Research、工作流、历史和私人材料。按需记录路径、标题、编号、状态与版本线索，不把所有 Markdown 当成现行规格。

默认只读。用户已要求修复时，可处理已证实的链接、索引、路径引用和有充分依据的状态问题；不顺手重写正文、移动文件、删除历史、替用户决定产品规则或执行 Git 写操作。先检查工作区，保留已有改动。

## 2. 检查入口与引用

检查范围内的入口、README、相对链接、HTML `href`、旧路径和标题锚点。

| 现象 | 判断 |
| --- | --- |
| 当前入口或当前正文引用不存在目标 | 已确认问题；先排除历史映射语境 |
| 迁移报告、历史副本保留旧路径 | 通常是历史证据，不自动修复 |
| 文件存在但标题锚点不匹配 | 根据实际渲染器判定；缺少依据则待核实 |
| 文本中只有旧文件名，没有链接 | 检查是否误导当前操作，不机械替换 |

明确区分全量解析、静态抽样与未检查；统计时说明是否包含 README、任务书、报告和历史副本。修复路径前验证新目标确实存在，并回查受影响的入口。

## 3. 检查规则、状态和主来源

关注以下关系：

- 术语在领域定义、需求和规格中是否同义；
- 已替代规则是否仍作为现行指令出现；
- 完成标记是否有实现或验收依据，研究交付是否被误写为采纳；
- 编号、文件名、标题、索引与任务书/报告配对是否一致；
- 数量、版本、日期和结构是否与实际范围一致；
- 同一规则是否有互相冲突的现行主要来源。

先按项目明确的权威来源、状态和替代关系判断。最新日期不能单独证明哪份更权威；无法判断时保留双方证据，列为待核实，不擅自裁决。

区分重复权威来源、合理摘要/引用和历史副本。迁移报告与现在不同可说明其历史范围或过期之处，不改写历史来迎合现状。已确认新决定需要落点时使用 `decision-to-spec`；文档体系缺失时可建议用户主动使用初始化流程，本次不自动扩为治理重建。

## 4. 使用项目检查器

有相关检查命令时，先读取其文档、帮助或实现，了解实际输出和退出码约定；不预设所有工具的 `0/1/2` 含义。

| 结果 | 处理 |
| --- | --- |
| 按工具约定成功且覆盖目标 | 仅声明该机械范围通过，警告逐项判断 |
| 输出并核实失效链接或规则问题 | 记录具体问题，按影响判定总状态 |
| 用法、输入、依赖或环境使检查未完成 | 记录工具失败；关键结论因此缺失时为阻塞 |
| 退出码含义未知或与实物矛盾 | 保存命令、退出码和输出，列为待核实 |

自动化不可用时继续能独立完成的静态检查。未运行的自动化标为未执行，既不能伪称自动通过，也不能抹去已有静态证据。

## 5. 交付发现与结论

每项发现给出证据、影响、优先级和下一动作，区分“问题、待优化项、建议、待核实项”。无发现的已检查范围可合并说明，不必为每类创建空表。

总状态按证据判断：

- **不通过**：有失效现行入口、规则冲突、关键索引缺失或重复权威来源等已证实的核心问题。
- **阻塞**：无上述已证实问题，但无法访问核心文档或缺少判定现行来源的关键依据。
- **部分通过**：核心文档可用，仍有不阻塞的导航、状态或维护问题。
- **通过**：检查范围内无已确认问题；非核心待核实项另列，不能宣称其已通过。

报告注明已检查、抽样与未检查范围；局部审计结论不能泛化为全仓库健康。若本轮已修复问题，复核后报告当前状态，同时保留已修复清单。

默认在对话中交付。用户要求保存或项目规则指定记录时，沿用项目目录，否则用 `.scratch/reports/docs-integrity-audit/<YYYY-MM-DD>-<范围>.md`。不改变公开/私有或 Git 忽略边界；保存位置有歧义时只澄清该动作，不阻止交付审计结论。

同一会话直接复用证据；跨会话才补充范围、已修复项、证据位置和剩余动作。本次结论不自动成为项目长期规则。
