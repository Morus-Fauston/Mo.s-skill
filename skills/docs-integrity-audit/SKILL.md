# 文档完整性审计

这个 Skill 用于检查一个已经演进了一段时间的文档体系是否仍然可信。重点不是润色文字，而是找出会误导人或 Agent 的结构性问题：链接失效、索引漏项、旧规则残留、状态漂移、重复权威来源、编号冲突和迁移记录过时。

## 完成条件与上下文摘要

- 维护参考：`skills/_shared/references/work-item-contract.md`、`skills/_shared/references/evidence-status.md`。
- 完成条件：审计范围、入口、引用、状态、权威来源和历史边界都有证据与结论；无法判断的项已标为 `待核实`。
- 只有跨 Agent、跨会话或长期留档时，才摘要审计范围、证据、已确认机械修复、未决问题和下一步；默认不创建过程文件。
- 发现已确认决定没有文档落点时调用 `decision-to-spec`；发现产品或术语分歧时，停止裁决并交给用户或讨论流程。

## 操作边界

- 默认只读审计。可以读取、搜索、解析和统计文档，但不删除、移动、重命名或大规模重写文件。
- 用户明确要求修复时，只修复已证实的链接、索引、状态和路径问题；不要顺手重写正文或改变产品决策。
- 历史文档、迁移报告、旧副本和归档材料默认保留。历史内容中的旧路径不自动视为当前失效引用。
- 不把一次性审计报告直接写成项目长期规则；只把稳定的治理原则提炼到项目指令或工作流文档。
- 报告是否公开、是否进入 Git 不明确时，先检查 `.gitignore` 并询问，不执行 `git add`、commit 或 push。

## 工作流程

### 1. 建立文档清单

先读取项目指令、术语表/领域模型、README 和文档入口，确定哪些目录属于：

- 现行术语和领域定义；
- ADR/架构决策；
- PRD、设计规格和开发规划；
- Research/任务书；
- 工作流、辅助记录和迁移报告；
- 历史归档或私人验证材料。

记录文件路径、标题、文档类型、状态、编号、版本和最后修改线索。不要把整个仓库所有 Markdown 都当成同一层级的现行规格。

### 2. 检查索引和链接

检查文档入口、各目录 README、目录表、Markdown 相对链接、HTML `href`、文档中的旧路径和标题锚点。

对每条引用分类：

| 类型 | 结论 |
| --- | --- |
| 当前入口指向不存在文件 | 问题 |
| 当前文档正文指向旧路径 | 问题，除非明确是历史映射 |
| 迁移报告中的旧路径 | 通常是有意保留，不算问题 |
| 历史副本中的旧路径 | 默认不算问题，但报告中说明范围 |
| 链接目标存在但标题锚点不匹配 | 问题或待核实，取决于渲染器证据 |
| 只有文件名文本、没有链接的历史记录 | 不自动修复 |

不能运行完整链接解析时，明确区分“已全量解析”“已静态抽样”“未检查”，不要把抽样结果写成全量通过。

### 3. 检查文档治理一致性

重点检查以下关系：

1. 术语表/领域模型中的术语是否在需求文档、决策记录、规格中保持同一含义；
2. 现行文档是否还保留已废弃决策或旧方案；
3. 版本规划是否包含已经完成的事项，或把未完成事项错标为完成；
4. 文档编号、文件名、标题和索引是否一致；
5. 任务书、研究报告、迁移报告的编号和配对是否完整；
6. 同一规则是否出现两个互相冲突的“主要来源”；
7. 文档中的数量、版本号、状态、日期和目录结构是否与当前文件树一致。

发现两种说法不同时，不要立刻判定冲突。先判断文档层级和时效：当前明确决策/现行规格 > 最新 ADR > 当前规划 > 旧规划 > 历史归档。无法判断哪份是现行来源时，列为“待核实”，不要替用户做决策。

### 4. 检查重复和迁移风险

区分三种情况：

- **重复权威来源**：两份现行文档都声称自己是同一规则的主要来源，必须提出归并或指定唯一来源的建议；
- **合理引用**：一份文档定义规则，其他文档只引用或摘要，不算重复；
- **历史副本**：明确标记为旧副本、归档或迁移记录，不删除，不算现行重复。

文件重命名/移动后，检查旧文件名、旧目录、编号和标题是否还出现在当前入口、正文链接、README 或自动生成清单中。迁移报告要和当前文件树对照，指出报告过期而不是重写历史。

### 5. 分级记录发现

每个发现必须有证据、影响范围和优先级，并分为：

| 分类 | 含义 |
| --- | --- |
| 问题 | 已确认会误导读者/Agent、使入口失效或造成现行规则冲突 |
| 待优化项 | 当前可用，但索引、状态字段、导航或维护性不够好 |
| 建议 | 基于审计结果提出的治理改进，不代表当前缺陷 |
| 待核实项 | 证据不足，不能判定为问题或通过 |

不要把“没有发现”与“没有检查”混为一谈。每一类都要明确写“本轮未发现”或列出具体项目。

### 6. 输出审计报告

默认在对话中交付报告正文并说明建议路径，不创建文件。只有用户明确要求落盘，或项目规则已明确指定文档审计、迁移记录或验证反馈目录时，才写入报告。报告使用以下结构：

```markdown
# 文档完整性审计报告

## 结论
- 总状态：通过 / 部分通过 / 不通过 / 阻塞
- 文档清单：X 个
- 当前入口：通过 X 个，问题 X 个
- 链接和路径：通过 X 个，问题 X 个，待核实 X 个
- 术语和规则冲突：X 个
- 状态/编号/版本漂移：X 个
- 重复权威来源：X 个
- 历史材料：保留 X 个，未删除

## 审计范围与方法
- 已检查：
- 静态抽样或全量解析：
- 未检查及原因：

## 问题
| 问题 | 证据 | 影响范围 | 优先级 | 建议修复 |
| --- | --- | --- | --- | --- |

## 待优化项
| 待优化项 | 证据 | 为什么不阻塞 | 优先级 | 建议时机 |
| --- | --- | --- | --- | --- |

## 建议
| 建议 | 依据 | 预期收益 | 建议时机 |
| --- | --- | --- | --- |

## 待核实项
| 待核实项 | 当前证据 | 无法定论原因 | 下一步验证 |
| --- | --- | --- | --- |

## 迁移与索引结果
| 来源文件/目录 | 目标或现状 | 结果 | 备注 |
| --- | --- | --- | --- |

## 后续动作
1. [具体动作]
```

总状态规则：

- **通过**：现行入口、关键链接、规则和状态均无已确认问题；待核实项不涉及核心入口。
- **部分通过**：核心文档可用，但存在不阻塞的导航、状态字段或维护性问题。
- **不通过**：存在失效当前入口、现行规则冲突、关键索引漏项或重复权威来源。
- **阻塞**：无法访问核心文档、无法区分现行与历史来源，或缺少判断冲突所需的关键决策记录。

## 与相邻 Skill 的边界

- 用 `decision-to-spec` 把新决定写入正确文档；本 Skill 负责一段时间后的体检。
- 用 `grill-with-docs` 解决术语和方案本身的分歧；本 Skill 不替用户做产品决策。
- 用 `check` 审查代码、发布和 Git 状态；本 Skill 只审计文档体系。
- 用 `phase-acceptance` 验收实现是否符合规格；本 Skill 不判定产品功能是否完成。

## 常见误判

- 迁移报告保留旧路径不等于当前链接失效；先看它是不是历史映射。
- 文件数量不一致可能是 README、任务书、报告或历史副本的统计口径不同；先拆分统计口径。
- 文档标题带旧编号不一定是链接问题，但可能误导读者，应列为待优化或问题并说明影响。
- 没有自动解析器时，不要声称“所有链接已通过”。
- 看到两份相似文档不等于重复权威来源；先检查状态、用途和交叉引用。
