# MAT 排错：先证明症状，再修根因

完成标准不是“测试变绿”，而是能用证据解释原症状，并区分已证实的修复、仅诊断结论和仍无法验证的部分。只有名字为 `hunt` 的这一份 MAT 适配入口；不再并列加载 `diagnosing-bugs`。

基于 Waza `hunt` 和 Matt Pocock `diagnosing-bugs` 改写，保留根因驱动与有效反馈回路，调整 MAT 授权、协作、Git 和交付边界。来源与许可见 [UPSTREAM.md](UPSTREAM.md)。**本目录只用于 MAT 的裁剪目录，不替换个人 Waza 版本。**

## 先锁定当前问题与责任

- 从真实任务、源会话和角色关系确定目标、写域及修复授权。请求“排查／为什么”只授权诊断；当前尚未完成任务已有明确修复授权时直接复用，不重复申请同一范围。
- 读取当前版本、实际触发入口、错误原文及相关源码／配置。旧报告与记忆用于找线索，不能替代本次原症状及现行实现；先查实际被执行的副本，不凭同名文件修改。
- 调查可以诊断取证探针，审阅可以诊断复现环境；二者都不能借排错修改被审业务成果。确需改成果或扩范围时，关联证据交主负责人／主管处理。
- 保留他人的暂存、未提交修改和作业。已授权的复现脚本及临时诊断只写自己的材料域；文件可写不等于可以覆盖别人的成果。
- 本方法不创建原生子代理或额外管理层。开发／调查主执行的一层协作资格仍由 MAT 记录决定，辅助和审阅会话不继续调辅助。需要协调时使用当前合法 Chat／请求入口，不伪装成用户或主管。

## 建立真正能抓到错误的反馈回路

选能触及实际故障的一条最小检查：已有测试、带固定输入的 CLI、HTTP 请求、界面动作、事件记录回放或有界探针。不要为凑流程重写已有充分复现。

**在修改前至少实际观察一次原症状。**同时确认：

1. 检查到达了原先出错的入口、版本、配置和状态，而不是邻近的另一个故障。
2. 判据针对具体错误结果，不仅检查“没有崩溃”“命令退出成功”。保留命令／动作、输入、输出、环境和证据位置。
3. 测试会因该症状真正失败。负向断言须有能使其失败的对照，检查框架不能吞掉中途断言、过滤全部用例或误把零测试算绿。
4. 缩减场景时逐步重跑，留下触发错误的必要条件；不会再失败的“最小场景”不能证明原问题不存在。

偶发错误记录重现率、时间顺序和代表性失败，不要求用不存在的确定性来宣称复现成功。压力、重复请求或故障注入只能在获准且不会污染真实数据的环境进行；运行次数由场景决定，不机械凑样本。

无法复现时可以读取源码解释候选原因，但**候选仍是假设，不能据此宣称根因或盲改**。列明已试方法、缺少的环境／输入，以及下一项最能区分原因的检查；需要真人或生产条件时向责任入口说明，不擅自加生产日志、索取凭据或启动替代服务。

## 用证据缩小原因

- 每个假设写清预期现象和反证方式，一次只改变能区分原因的变量。证据不符就放弃或修订，不往已被推翻的假设上继续打补丁。
- 沿输入、状态、调用、输出追踪首个偏差。根因解释必须能覆盖关联症状；无法解释的差异保留，不一概归为“缓存问题”。
- 行为／生命周期／并发问题优先检查时间戳、事件顺序和状态归属；每条诊断日志都应回答一个具体问题，不记录敏感负载或整份环境变量。
- 性能问题先测同环境基线，再比较同样输入下的时间、资源或分布；不能用“感觉更快”替代测量。
- 回归先比较已知正常版本与当前版本的相关变化。`bisect`、切换分支、工作树创建／删除及重置都是独立操作，不能从诊断授权推导；没有相应授权就用可取得的差异和材料检查，不操作共享 Git 现场。
- 原生界面、生成文件或工具故障先分清底层与上层：构建成功不证明已在目标环境生效，启动失败不等于被测产品逻辑失败。
- 同一修正后原症状仍在，回到证据链，而不是再猜一个参数。反复无新证据或缺关键条件时，回报阻塞与下一验证动作，不无限试错，也不强制按固定猜测次数重建任务。

## 在原授权内修复与回归

1. 能说明“哪里、在什么条件下、为什么产生原症状”并有对应证据后，只修复所需范围。必要的接口修正可说明原因；无关重构、功能扩展另行安排。
2. 适用时先留下会失败的回归测试，再修复并观察它通过。使用足够高的真实入口；过浅测试抓不到原调用链时明确证据缺口，不能靠假测试交差。
3. 重跑原始完整场景和受影响检查，而不只跑简化用例。复现红态可使用获准的隔离夹具或已有旧版证据，不为证明红绿去回滚、隐藏或清理共享工作区。
4. 检查同一已证实根因模式可能影响的相关位置，区分同类问题、无害命中和待核实。只修已有授权覆盖的部分，不因一次搜索开启全仓整改。
5. 处理本轮新增的诊断材料，重要原始失败证据保留；清理仅限明确属于本轮且获准处置的临时内容，不默认删除所有探针或别人的日志。

测试、构建、静态阅读、模拟、真实设备和人工体验分别报告。缺必需真实环境结果时，结论是“局部证据已取得，整体仍待验证”，不是“全部修复”。

## 回报与交付

简明说明：**原症状、已证实根因或当前假设、修改范围、红态／绿态证据、相关影响、未验证项和下一责任**。无事实的字段不强填，不要求固定长报告。

- Log 是否写入由工作需要决定；更新 Checklist 必须关联已有或同次新 Log。辅助只更新主负责人通过 Chat 明确授予的指定项，不能因“负责测试”推定勾选权。
- 诊断结束不自动等于整票完成。当前任务确已完成时按 MAT 的完成 Chat 交回；无可做部分按挂起 Chat 说明等待对象／恢复条件，原暂停仍有效。工具缺失或回执不明如实报告，先核原记录，不重复派工或重做未知副作用。
- **不执行 Git 暂存、提交、推送或发布，不自动生成会话交接、不改变票据状态。**主执行成果仍须独立审阅，作者测试和自查不能替代独审。
