# 调研任务书

这个 Skill 的职责是让独立 Agent 能在不依赖当前对话的前提下完成一次有边界的调查。它负责界定问题、准备已知事实、证据标准、输出路径和验收条件；任务书交付后由用户自行决定是否派发、派给谁以及使用什么研究流程。它不自行检索取证、不调用 `research`、不接收研究结果，也不把候选建议写成正式项目决定。

## 完成条件与上下文摘要

- 维护参考：`skills/_shared/references/work-item-contract.md`、`skills/_shared/references/confirmation-gates.md`。
- 完成条件：任务书的范围、问题、硬事实、证据标准、交付物、接收条件和用户派发决定都已明确。
- 调研任务书本身已经是跨 Agent 输入，不再额外创建交接表；需要跨会话继续时，只摘要决策问题、范围、证据标准、交付物、未决问题和下一步。
- 用户确认派发后交给 `research`；研究结果回来后，由用户决定是否交给 `decision-to-spec`。

## 适用边界

- 默认遵循用户语言和项目文档语言；源码、API 名称和原始引用保留原语言。
- 调研对象可以是本地源码、官方文档、运行时行为、第三方库、竞品、技术路线或迁移成本。
- `research-brief` 负责是否值得外包与任务书；用户可自行选择使用 `research` 或其他约定流程完成实际调查。
- `learn` 面向建立通用知识模型或长文；本 Skill 面向一个会影响项目下一步的具体问题。
- 用户需要体验并拍板交互时，使用 `interaction-prototype-to-spec`，不要伪装成独立调研。
- 用户只问一个可通过一次有界查阅确认的小问题时，直接查阅；不要创建任务书。

## 1. 判断是否值得外包

先读取项目关于调研委托的政策或 ADR。没有明确政策时，只有同时满足以下条件才创建任务书：

1. **无法快速可靠确认**：检查项目入口、一次目标搜索和一个主要来源后，仍不能用直接证据回答；
2. **事关紧要**：结论会影响设计决策、编码正确性、许可证、迁移或性能风险；
3. **可独立执行**：范围、资料入口和判定标准可以写清，不依赖主 Agent 的 UI 状态、会话上下文或用户现场判断。

不满足时，说明为什么直接查阅更合适。不能因为用户说“调研”就机械创建任务书。

## 2. 建立可执行任务书

满足外派条件后，读取邻近 PRD、规格、ADR、既有调研、术语表和实现约束。只记录已实际核实的事实，防止受托 Agent 重复劳动或推翻既定约束。

任务书必须包含：

| 项目 | 必须写清 |
| --- | --- |
| 背景 | 为什么调研，当前阻塞哪个设计或编码决策 |
| 已核实硬事实 | 已由本地代码、配置、测试或第一方资料确认的事实、限制与来源 |
| 调研问题 | 使用 `Q1/Q2/...` 编号；每项包含问题、搜索线索和可判定的完成条件 |
| 范围与非目标 | 要看的模块、版本、资料、明确不看的内容与不应替用户决定的事项 |
| 证据标准 | 高影响结论优先本地实物、官方源码、规范或第一方 API；第三方资料只能做线索或对比 |
| 期望产出 | 逐题结论、证据定位、方案比较、风险、未确认项和建议的下一步 |
| 执行约束 | 只读、不改代码、不编造路径/行号、冲突保留、无法确认时如实标记 |
| 交付位置与命名 | 项目约定目录、文件名、是否更新索引及结果如何回报 |

每个问题要说明它需要证明什么，不要下发“自行判断”而没有判定标准。涉及公式、坐标、尺寸、解析或渲染时，明确要求受托 Agent 使用真实代表性样本验算；没有样本时只能提出验证计划。

## 3. 交付任务书

任务书完成后交付给用户，并明确：

1. 本 Skill 到此结束，不自动派发、不调用 `research`，也不等待研究结果；
2. 用户决定是否派发、派给哪个独立 Agent、是否使用 `research`，以及何时将结果带回项目；
3. 研究结果中的建议不自动成为决定；需要采纳时，由项目决策者确认后使用 `decision-to-spec` 同步到 ADR、需求、规格或术语表。

## 5. 交付前检查

- 任务是否同时满足无法快速可靠确认、事关紧要和可独立执行；
- 已核实硬事实没有混入猜测，且来源已实际核对；
- 每个 `Q` 有搜索线索和完成条件，不要求受托 Agent 猜意图；
- 范围、非目标、只读限制、输出路径和命名清楚；
- 高影响结论的证据标准与冲突处理方式明确；
- 涉及真实样本时已明确样本和验算要求，缺少样本时没有暗示已验证；
- 任务书没有冒充最终调研报告、ADR 或正式规格；
- 任务书已明确由用户派发，且不把未来研究建议自动升级为决定。

## 常见失败模式

- 为几次查阅就能确认的问题建立外包任务书；
- 只写研究主题，不写问题、范围、完成条件和证据标准；
- 把受托 Agent 的建议写成已经采纳的决定；
- 要求“查源码”却不写版本、模块、搜索线索或输出路径；
- 把第三方文章当成关键事实的唯一证据；
- 研究结果回来后只看推荐，不核对证据缺口和无法确认项。
