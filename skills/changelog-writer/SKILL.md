# 更新日志与版本记录

分析上一个版本以来的 Git 改动，起草两份更新日志文件（详细 Markdown 与精简纯文本），再按用户确认选择是否提交和推送。

## 为什么使用两份文件

- `CHANGELOG.md`：供开发者和审阅者阅读的完整记录，允许表格、子要点和 Markdown。
- `CHANGELOG.txt`：方便快速浏览的压缩纯文本记录。

两份文件必须同时更新，内容相同但详略不同。`CHANGELOG.txt` 中的新版本条目同时作为 Git 提交信息。

## 工作流程

### 1. 收集改动

从以下两类来源收集信息：

**A) Git 历史**：代码库实际发生了什么改动。

```bash
# 查找最后一次改动任一更新日志文件的提交
git log -1 --format="%H" -- CHANGELOG.md CHANGELOG.txt

# 获取此后的已提交改动
git diff --stat <that-commit>..HEAD
git log --oneline <that-commit>..HEAD

# 同时检查未提交改动
git status --short
git diff --stat
git diff --cached --stat
```

仓库有版本标签（例如 `v0.2.0`）时，优先使用最新标签作为基线。

**B) 当前会话上下文**：本轮讨论和确认过什么。

当前会话通常比 diff 包含更多背景：设计决定、采用某个方案的原因、试过又放弃的做法和用户意图。应将这些背景写进更新日志，而不是只罗列文件名。例如用户说“我把武器编辑器拆成了多态组件因为以后要加能力编辑”，更新日志应记录这个架构动机，而不是只写“重构武器编辑器”。

阅读实际 diff，理解改了什么，而不只是哪些文件变化；再结合会话上下文理解为什么改。按“修复 / 新增 / 调整 / 架构改进 / 体验优化 / 文档 / 技术”分类。

项目存在自己的更新日志规则文档（例如 `Docs/Changelog规则.md`）时，先读取并优先遵循它；否则遵循 `references/changelog-format.md` 的默认规则。

### 2. 起草更新日志（内部完成，暂不询问用户）

从 `CHANGELOG.md` 最新条目读取当前版本。展示标题或 Git 标签可以使用 `v` 前缀，但版本本体必须是标准 SemVer 的 `MAJOR.MINOR.PATCH`，例如展示为 `v0.4.0` 时，版本本体是 `0.4.0`。

根据改动性质自动建议版本号：
- **PATCH**（+0.0.1）：向后兼容的缺陷修复。
- **MINOR**（+0.1.0）：向后兼容的新增功能。
- **MAJOR**（+1.0.0）：不兼容的公开接口、行为或数据格式变更。

仅文档、内部重构或配置调整不必然要求发布版本；是否发布以项目规则和用户决定为准。已经发布的版本不得修改原有条目；需要修复时，发布下一个 PATCH 版本。

需要提前试用而不发布正式版时，使用标准预发布标识：
- `0.5.0-alpha.1`：早期试验，接口和行为仍可能大幅调整。
- `0.5.0-beta.1`：功能基本完成，等待更广泛试用。
- `0.5.0-rc.1`：候选发布版，除阻塞问题外不再新增功能。

预发布标识中的数字递增，例如 `0.5.0-rc.1 → 0.5.0-rc.2`。正式发布时移除预发布后缀，例如 `0.5.0-rc.2 → 0.5.0`。Git 标签可使用 `v0.5.0`，但更新日志和依赖清单中的版本本体仍写 `0.5.0`。

使用当前系统时间作为时间戳，格式为 `YYYY-MM-DD HH:mm`。

根据收集到的改动同时起草两份更新日志。此时不得写入文件，应保留草稿等待确认。

完整格式规则见 `references/changelog-format.md`。

**`CHANGELOG.md` 的关键结构：**

```markdown
## vX.Y.Z (YYYY-MM-DD HH:mm)

### 分类标题

- **关键词**：一句话描述改了什么、为什么改
  - 子要点（可选，用于多步骤/多状态说明）

### 文件变更表（功能版本或主版本附带）

| 文件 | 变更 |
|:-----|:------|
| `path/file.py` | **新增** — 说明 |
| `path/file2.py` | 修改了什么 |
```

写作规则：
- 每条以**加粗关键词**开头，后接中文冒号 `：`。
- 修复类条目写清“现象 → 根因 → 修复方案”。
- PATCH 和预发布版本可省略文件变更表。
- MINOR 和 MAJOR 版本应包含文件变更表。
- 使用 `---` 分隔新旧版本条目。

**`CHANGELOG.txt` 的关键结构：**

```
vX.Y.Z (YYYY-MM-DD HH:mm)
  分类: 一句话压缩总结
  - 要点1
  - 要点2
```

- 一行能说完时保持一行，多项使用 `/` 或 `|` 分隔。
- 子项使用 2 个空格缩进。
- 大版本块之间使用 `====` 分隔线。
- 不使用 Markdown 格式，只写纯文本。

### 3. 一次性确认（一次交互收集全部决定）

这是唯一需要暂停等待用户输入的环节。当前 Agent 运行环境提供原生问答或选项工具时，优先在一次交互中展示草稿并收集全部决定，而不是拆成自由对话式的多轮确认。当前环境没有此类工具时，才退回普通对话确认。

**向用户展示：**
1. `CHANGELOG.md` 的完整草稿条目。
2. `CHANGELOG.txt` 的完整草稿条目。
3. 版本号建议及理由。

**一次询问全部问题：**
- **版本号**：确认建议版本，或填写其他版本号。
- **内容修改**：是否修改两份草稿？留空表示按草稿通过。
- **Git 动作**（单选）：
  - 只写入更新日志。
  - 提交已复核文件，不推送。
  - 提交已复核文件并推送。
- **暂存范围**：展示拟提交的准确文件，并允许用户通过窗口的自由文本字段修改清单。默认不得包含工作树中无关的文件。
  - 不提交任何文件，只写入更新日志。

不得拆成多轮确认。选择器窗口必须一次收集全部决定。选择提交时，在暂存前再次展示最终批准的暂存清单；这只是复核展示，不是新的确认轮次，除非暂存范围发生变化。

### 4. 执行

用户确认后：

1. 应用用户要求的内容修改。
2. 写入 `CHANGELOG.md`：将新条目放在最顶部；如果存在 `# Changelog` 标题，则放在标题之后、全部旧条目之前。
3. 写入 `CHANGELOG.txt`：将新条目放在最顶部。
4. 执行用户选择的 Git 动作。

**选择“不提交任何文件”时：**停止，并说明日志已写入。

**选择“提交已复核文件”（无论是否推送）时：**

1. 展示最终暂存清单，并确认其中只有两份更新日志和用户批准、与本次发布相关的文件。
2. 禁止使用 `git add -A`、`git add .`，以及任何将未复核工作树整体暂存的命令。
3. 明确逐个暂存已复核路径。用户要求提交整个工作树时，先展示完整清单；在暂存前单独取得明确确认。

```bash
git add -- CHANGELOG.md CHANGELOG.txt <reviewed-path-1> <reviewed-path-2>
git commit -m "<the full txt entry block>"
```

提交信息必须**完全等于新的纯文本条目**，也就是写入 `CHANGELOG.txt` 的该版本完整区块。不得添加前缀、后缀或 Conventional Commit 标签。暂存路径必须与已复核范围一致。

用户选择“提交并推送”时，再执行：

```bash
git push
```

## 边界情况

- **基线后没有改动**：说明没有可记录的内容，不创建空条目。
- **首次版本**：`CHANGELOG.md` 不存在时，创建包含 `# Changelog` 标题和首个条目的文件；`CHANGELOG.txt` 同理。
- **用户提供具体说明**：以用户说明为主要内容，再用 Git diff 补齐事实。
- **范围内存在合并提交**：总结最终影响，不逐条罗列每个合并提交。
- **改动集很大**：聚焦用户可感知的影响和架构决定；把相关小改动归类，不逐个文件机械罗列。
