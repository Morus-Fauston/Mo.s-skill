# 更新日志与版本记录

分析上一个版本以来的 Git 改动，起草两份更新日志文件（详细 Markdown 与精简纯文本），再按用户确认选择是否提交和推送。

## 完成条件与上下文摘要

- 完成条件：双日志内容与版本明确，用户选择的写入或 Git 动作完成；仅要求草稿时交付草稿即可，提交范围只在需要提交时复核。
- 同一上下文继续工作时不需要输出固定表格；只有跨 Agent、跨会话或长期留档时，才摘要版本、证据、暂存范围、未决问题和下一步。
- 用户要求审阅草稿时交付后结束；待执行的写入或 Git 动作缺少确认时停在 `awaiting-user`。已有有效批准可复用。

## 为什么使用两份文件

- `CHANGELOG.md`：供开发者和审阅者阅读的完整记录，允许表格、子要点和 Markdown。
- `CHANGELOG.txt`：方便快速浏览的压缩纯文本记录。

两份文件必须同时更新，内容相同但详略不同。`CHANGELOG.txt` 中的新版本条目同时作为 Git 提交信息。

## 工作流程

### 1. 收集改动

从以下两类来源收集信息：

**A) Git 历史**：代码库实际发生了什么改动。

```bash
# 查找最后一次改动任一更新日志文件的提交
git log -1 --format="%H" -- CHANGELOG.md CHANGELOG.txt

# 获取此后的已提交改动
git diff --stat <that-commit>..HEAD
git log --oneline <that-commit>..HEAD

# 同时检查未提交改动
git status --short
git diff --stat
git diff --cached --stat
```

仓库有与当前目标分支和发布范围对应的版本标签时，优先用它作基线；不要盲选其他分支的最新标签。

**B) 当前会话上下文**：本轮讨论和确认过什么。

当前会话通常比 diff 包含更多背景：设计决定、采用某个方案的原因、试过又放弃的做法和用户意图。应将这些背景写进更新日志，而不是只罗列文件名。例如用户说“我把武器编辑器拆成了多态组件因为以后要加能力编辑”，更新日志应记录这个架构动机，而不是只写“重构武器编辑器”。

阅读实际 diff，理解改了什么，而不只是哪些文件变化；再结合会话上下文理解为什么改。按“修复 / 新增 / 调整 / 架构改进 / 体验优化 / 文档 / 技术”分类。

项目存在自己的更新日志规则文档（例如 `Docs/Changelog规则.md`）时，先读取并优先遵循它；否则遵循 `references/changelog-format.md` 的默认规则。

### 2. 起草更新日志（内部完成，暂不询问用户）

按项目版本规则和相关变更建议下一版本；没有项目规则时使用标准 SemVer。单纯文档、内部重构或配置调整不必然要求发布。破坏性变更置于首位并说明迁移动作，已发布条目不改写。

起草前读取 [格式规范](references/changelog-format.md)，按其中的双格式、版本和必要特殊段落要求生成内容，不另造格式。时间戳使用当前系统时间 `YYYY-MM-DD HH:mm`。这里只生成草稿，尚未获准时不写文件。

`CHANGELOG.txt` 中的新版本条目同时作为 Git 提交信息，因此两份文件必须由同一份草稿生成：先定分类和每条要点，再分别展开为 Markdown 条目与纯文本条目，不做两套独立写作。

### 3. 一次性确认（一次交互收集全部决定）

正常路径在此一次收集所需决定。先复用同一任务中仍有效的用户确认：版本、双日志内容、Git 动作和具体提交差异均已获准且未变时，复核后直接执行，不重复询问。只有决定缺失或批准内容发生实质变化时才询问相应缺项或变化。

需要询问时，使用当前环境可用且允许用于该类确认的原生问答或选项工具；没有适用工具时在对话中展示材料并收集确认，不因工具存在但用途受限而停住。

**向用户展示：**
1. `CHANGELOG.md` 的完整草稿条目。
2. `CHANGELOG.txt` 的完整草稿条目。
3. 版本号建议及理由。

**需要确认的决定如下；只问本次动作所需且尚未明确的项，可按工具能力合并：**
1. **版本号**（文本输入）：默认选择“确认建议版本号”；用户也可以填写其他合法 SemVer。
2. **草稿内容**（单选）：默认选择“确认两份草稿”；另提供“修改草稿”和“不写入日志”。
3. **Git 动作**（单选）：默认选择“提交并推送”；另提供“只写入更新日志”和“提交但不推送”。
4. **提交范围**（单选或文本输入）：默认选择“全部提交”；同时展示工作树中将被包含的完整文件清单，并提供“仅提交已复核文件”和“暂不提交”。

“默认选择”只是原生控件预选值，不是用户授权。用户未提交确认或取消窗口时，待执行动作停在 `awaiting-user`；明确改选其他项时按实际选择执行，不能沿用预选项。选择“全部提交”时，在这次确认中展示完整清单和对应差异，并允许用户删减。

暂存前复核批准与当前内容的对应关系，包括双日志、提交信息和完整待提交差异；仅文件名一致不足以证明批准仍有效。批准内容和动作未变时，展示复核结果后继续，不新增确认轮次；日志、版本、提交内容、范围或 Git 动作发生实质变化时，只就变化重新确认。未纳入提交的无关文件变化不使原批准失效。

### 4. 执行

用户确认后，先复核上述批准仍有效，再按所选动作执行：

1. 应用用户要求的内容修改。
2. 写入 `CHANGELOG.md`：将新条目放在最顶部；如果存在 `# Changelog` 标题，则放在标题之后、全部旧条目之前。
3. 写入 `CHANGELOG.txt`：将新条目放在最顶部。
4. 执行用户选择的 Git 动作。

**选择“不写入日志”时：**不写文件、不暂存、不提交或推送。**选择“只写入更新日志”或确认写入但暂不提交时：**只写双日志，说明未执行 Git 写操作。

**选择“提交已复核文件”（无论是否推送）时：**

1. 展示最终暂存清单，并确认其中只有两份更新日志和用户批准、与本次发布相关的文件。
2. 禁止使用 `git add -A`、`git add .`，以及任何将未复核工作树整体暂存的命令。
3. 明确逐个暂存已复核路径。“全部提交”的批准同样复用，不另设确认门。暂存后核对整个索引与批准差异一致；存在未批准内容时不提交，也不擅自撤销他人的暂存。

```bash
git add -- CHANGELOG.md CHANGELOG.txt <reviewed-path-1> <reviewed-path-2>
git commit -F <utf8-message-file>
```

将新的纯文本条目完整写入临时 UTF-8 提交信息文件，再用 `git commit -F` 读取，避免多行文本被 shell 改写。提交信息必须**完全等于新的纯文本条目**，不得添加前缀、后缀或 Conventional Commit 标签。暂存路径必须与已复核范围一致。

用户选择“提交并推送”时，再执行：

```bash
git push
```

## 边界情况

- **基线后没有改动**：说明没有可记录的内容，不创建空条目。
- **首次版本**：`CHANGELOG.md` 不存在时，创建包含 `# Changelog` 标题和首个条目的文件；`CHANGELOG.txt` 同理。
- **用户提供具体说明**：以用户说明为主要内容，再用 Git diff 补齐事实。
- **范围内存在合并提交**：总结最终影响，不逐条罗列每个合并提交。
- **改动集很大**：聚焦用户可感知的影响和架构决定；把相关小改动归类，不逐个文件机械罗列。
