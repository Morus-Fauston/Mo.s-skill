# Skill 工作流可视化

让用户看清何时选哪个 Skill、Agent 会做什么、哪里需要人决定，以及结果如何进入下一环节。每条关系须有当前正文或调用配置依据，不能根据名称补出流程。

## 1. 确定范围和来源

优先分析用户点名的 Skill，其次是当前工作流中与目标直接相关的 Skill；只有全量盘点请求才扩至对应作用域。读取项目指令与当前入口，记录实际路径、所属 Agent/来源、版本或更新时间线索。缺失路径如实说明，不推断内容。

同名跨 Agent 入口可能是同步副本，先核对来源与正文；触发竞争按实际共同可发现的作用域判断，不将副本数当来源数。

默认只读。请求更新现有流程图时可修改该图及其必要说明，不借机改 Skill、安装清单、业务代码或 Git 状态。

## 2. 从正文提取事实

读取 frontmatter、足以决定行为的正文、调用配置及被明确引用的相关约束。每个 Skill 提取：

| 事实 | 内容 |
| --- | --- |
| 触发与前提 | 请求意图、输入、环境、权限、已有决定 |
| 自动步骤 | 可自行读取、检查、生成和验证的动作 |
| 人工关口 | 仍待明确的选择、体验、凭据或执行授权 |
| 输出与完成条件 | 产物、结论、状态，什么时候结束 |
| 转交与禁止项 | 进入下一项的条件、调用方式与职责边界 |

区分“正文规定”“配置允许”和“运行中已观测到”；写着自动调用并不证明当前 Agent 能加载它。引用内容冲突时按项目指定优先级判断，仍不清楚则标待核实。

## 3. 按需检查历史模式

仅当用户明确要求统计常用 Skill 或跨项目工作流且有可访问历史时执行。说明项目/时间/字段覆盖，提取使用频率、起点、先后关系与反复停顿等聚合信号；不导出无关对话、凭据或业务细节。

历史顺序不等于当前必需流程，使用次数不等于价值。历史不可用时继续完成正文分析，明确限制。涉及取舍、精简或新 Skill 候选，可整理事实并建议用户主动调用 `skill-workflow-orchestrator`，不自动改造。

## 4. 选择表与流程图

简单线性关系用文字或表格即可；用户明确要求画图，或存在多入口、条件转交和人工关口时再画。总览展示入口与条件，只有复杂内部流程才另画单 Skill 图，不为每个 Skill 强制配图。

连线标注实际含义：

| 关系 | 建议画法 |
| --- | --- |
| 当前流程明确自动转交且调用策略允许 | 实线，标“自动调用”与条件 |
| 仍需用户决定/授权 | 实线，标“用户确认”，关口写“等待用户” |
| 推荐后续方向 | 虚线，标“建议” |
| 由用户或独立执行者负责 | 实线，标“外部执行”与责任方 |

如果正文与调用策略冲突，不选择一方画成已生效行为；在图旁列出冲突。已有有效授权可以复用，不能把流程图的关口画成每次都重新询问。

研究完成不等于采纳、计划批准不等于授权实施、原型完成不等于规则已确认。节点保持短而单一；按可读性拆分复杂图，不设硬性节点配额。

需要完整文档时按需读取 [输出模板](references/workflow-template.md)。小范围回答只保留选择理由、关系证据与未核实项。

## 5. 核对并交付

逐条核对图表与当前正文/配置：入口是否存在、条件与人工关口是否完整、建议是否误画为自动、统计与路径是否对应本次范围，Mermaid 围栏是否闭合。

更新旧图时说明“旧关系 → 当前关系 → 证据”，只改已证实过期的部分。未读取或不能确认的内容单列；不把局部检查写成全量通过。

默认对话交付。用户要求保存/更新时沿用项目位置；只在跨会话或跨 Agent 时额外摘要分析范围、来源、未决问题和下一步，不制造重复过程文件。
