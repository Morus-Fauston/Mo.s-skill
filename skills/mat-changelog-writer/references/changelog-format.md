# MAT 专版默认日志格式

仅在工作项目没有相应规范时使用本文件；项目对日志文件、版本、提交信息任一项已有明确规定时，该项按项目执行。不改变主管确定的版本和写入范围，不借格式默认取得文件创建权限。

## 同源双格式

先确定同一组分类和事实，再展开为 `CHANGELOG.md` 与压缩的 `CHANGELOG.txt`。两者描述同一版本、范围、验证边界和未完成事项，不做两套独立写作。新条目置顶，Markdown 保留已有总标题和全部历史。

### Markdown

```markdown
## vX.Y.Z (YYYY-MM-DD HH:mm)

### 分类标题

- **关键词**：改了什么、为什么改
  - 必要的证据范围、迁移步骤或限制

### 文件变更表

| 文件 | 变更 |
|:-----|:-----|
| path/file.ext | 与本批实际差异相符的说明 |

### 已知问题
- 无

### 待完成
- 无

### 刻意不做
- 无
```

- 分类按内容选择：修复 / 新增 / 调整 / 架构改进 / 体验优化 / 核心重构 / 技术 / 文档；不填空分类。
- 条目以加粗关键词及中文冒号开头；修复说明现象、已证实根因和修复方式，未知根因不编造。
- 破坏性变更置于版本内容首位，写明旧行为到新行为及迁移动作。
- MINOR/MAJOR 附文件变更表；PATCH/预发布可省略。不列本批未包含的在途文件。
- 已知问题写本版本未修问题及影响；待完成写已承诺但未交付事项与后续条件；刻意不做写主动排除的范围及理由。三段分开，无内容写“无”，不虚构承诺。
- 新旧版本用 `---` 分隔。仅必要时添加阶段回顾或复杂修复历程，不为完整而加长日志。

### 纯文本与提交信息

```text
vX.Y.Z (YYYY-MM-DD HH:mm)
  分类: 一句话压缩总结
  - 必要要点
  [已知问题] 影响与追踪
  [待完成] 未交付事项与后续条件
  [刻意不做] 范围与理由
```

- 使用纯文本和 2 空格缩进，一行能说明则一行；多项可用 `/` 或 `|` 分隔。
- 三个特殊标签与 Markdown 一致；对应段为“无”时可省略标签。不能把“静态核对”压缩成“验证通过”。
- 新旧版本块之间使用 `====`；分隔线不属于新版本区块。
- 无项目提交信息规范时，提交信息**完全等于已审阅的 TXT 新版本完整区块**，不追加 Conventional Commit 前后缀；项目已规定其他格式时单独按其规范拟定并交主管审阅。

## 版本、时间与历史

- 默认版本本体使用 SemVer：`MAJOR.MINOR.PATCH`；可用 `-alpha.1`、`-beta.1`、`-rc.1` 等预发布标识，显示标题可加 `v`。
- 版本号由主管决定，不由提交员根据 diff 自动升级；未提供或与适用规则冲突时请主管澄清。项目另有日期版本等规范时不强套 SemVer。
- 准备时读取实际系统时间，格式 `YYYY-MM-DD HH:mm`；两份日志保持一致。主管批准后不为追求“最新时间”擅自重写批准材料。
- 已发布条目保留；需纠正时向主管提出后续版本/补充记录，不自行覆盖历史、创建修订后缀或重写 Git 历史。
- 日志中的交付、审计、人工验收与 Git 结果分别陈述；未执行的测试、不存在的证据或失败推送不能写成已通过。
